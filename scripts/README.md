## Fresh-data e2e runtime

The actual source and built platform entrypoints require a real Docker Unix socket and await reconciliation. `pnpm dev:bg` preflights the configured Engine. `pnpm e2e` instead provisions its own Docker and containerd runtime before main: nonroot Linux, installed `/usr/bin/dockerd`, `/usr/bin/containerd`, `/usr/sbin/ip`, Python3, util-linux `unshare` with PID/mount/network namespace support, and noninteractive sudo are required. Unsupported hosts (including macOS) fail closed; no shared-Engine fallback or image pull is performed. Run only reviewed trusted checkout code with that privilege. Build, main and the complete HTTP smoke client run together on the private namespace's loopback; printed loopback URLs are not host-facing listeners. The scenario remains nonroot and retains health and exact schema/migration ledger checks. CI's default daemon still serves dev-server smoke.

The private runtime uses containerd2.x configuration version3 and requires Docker's `/info` to identify its containerd address and container/plugin namespaces. Docker28.0.4 on hosted CI and29.1.3 on giap-vps have exercised this entrypoint; unknown or incompatible runtime identity fails closed. No daemon upgrade is performed. The supervisor captures two fresh0700 directories: privileged state stays UID0-only, while only the separate socket/temp directory is transferred to the caller. Both remain under the supervisor's cleanup authority, including caller death; no caller-supplied path is adopted. util-linux `unshare --fork` ignores group SIGINT/SIGTERM while waiting, so ordinary command cancellation reaches the owner through stdin EOF rather than bypassing its cleanup.

- Fresh-data e2e ignores inherited Engine selection and supplies its captured private socket. Docker/containerd storage and process isolation are supplemented by a separate kernel network namespace: unchanged caller identity is rejected before daemon/network mutation, and both daemon memberships are checked before main. Only private loopback is enabled; bridge/firewall flags alone are not isolation. Stdin EOF handles caller loss, and PID/mount containment retires descendants on supervisor death. Shutdown settles scenario, Docker and containerd before removing both captured directories; unconfirmed cleanup fails. `pnpm test:docker platform/test/e2e-engine.docker.test.ts` requires held employee-bridge survival, caller default-bridge identity preservation, namespace/prerequisite/identity/setup failure and process-death cleanup evidence. The read-only smoke suite does not start employees; future image/network/publication coverage needs separate qualification. Dev-server shared-Engine semantics and watcher issue#174 are unchanged.

## Background dev lifecycle

- Background start/stop serialize the complete PID-ownership transition with `.run/dev.lock`; concurrent lifecycle commands fail explicitly rather than claiming predecessor readiness. Stop retains `.run/dev.pid` and `.run/dev.stopping` until actual graceful exit; its30s timeout and signal interruption retain ownership and never force-kill to claim completion. ## Trusted Docker custody

`pnpm check` and `pnpm test:integration` never start Docker. Only the trusted parent session runs `pnpm test:docker` on giap-vps (Ubuntu 24.04/Linux amd64), after full review of the exact commit. Install Node 24.13.1 and pnpm 10.34.6 from `.tool-versions` below ubuntu's home, verify executable paths and versions, and leave system binaries/packages unchanged. Missing Docker/daemon/tool prerequisites fail, not skip.

For ordinary remote full-Docker custody, use `pnpm --silent verify:docker start <reviewed-sha>` from a prepared, dedicated, clean checkout of that exact commit on the qualified host. It does not install dependencies or build a different revision. The returned invocation identifies private records under `~/.local/share/dsh-team/docker-verification/`; the detached owner runs the original full `pnpm test:docker` with its existing discovery and deadlines. Keep that checkout frozen while work is active.

Reconnect with `pnpm --silent verify:docker status <invocation>` and retrieve `pnpm --silent verify:docker logs <invocation> stdout` or `pnpm --silent verify:docker logs <invocation> stderr`. Status-query success is not test success: inspect the recorded command exit/signal, interruption, output completeness and cleanup separately. Missing or changed authority fails closed; a missing owner without terminal evidence remains unknown. Launch observation is bounded but does not cancel the remote job, and an SSH disconnect is never a passing verdict.

Only `pnpm --silent verify:docker cancel <invocation>` requests cancellation. The owner verifies its captured child generation and separate process group before signalling; a signal sent only to pnpm is not child-settlement evidence. The original root command retains cleanup mutation ownership, with one exception: after the owner itself signalled its group and that group, its producers and browser producers settled, it retires the exact names and labels registered in the invocation's private journal, latest run first. Before any mutation every observer writer must be dead or absent, except a run's own exactly bound fixed platform, and a fresh invocation digest must still match. A run that registered the fixed platform is drained by exact-ID SIGTERM to a clean exit under the host-wide deployment lock, and every submission reservation must then have settled before its removal; otherwise nothing of that run is removed. Failures are recorded only as a private `retirement.json` count, never in the terminal: a cancelled run stays failed, and uninterrupted runs never retire. The custody observer remains read-only and performs only registered-target/browser-receipt and exact-absence checks; it alone decides confirmed cleanup. Uncertain creation or remaining work is unconfirmed, never PID-only signalling, foreign-resource deletion or global/prefix rescue. Output is streamed to private files with proxy/credential exclusion; partial evidence cannot qualify. This ordinary lane receives no model authorization or CI invocation marker and never publishes a GitHub success status itself. The trusted parent still requires actual SSH-disconnection/reconnection qualification, the original exact-head full suite, and independent owned retirement/unchanged protected-host evidence.

Custody process fixtures use the canonical kernel-derived Darwin birth format and reject obsolete display hashes. A directly spawned observer must reach its actual child-close/reaping boundary before group-absence observation: Darwin can report birth absence but `kill(-pgid, 0)` EPERM for the still-unreaped zombie. EPERM is never absence evidence. After the owned command's actual `close`, the custody owner observes its group within one bounded2000ms monotonic window at20ms: only `ESRCH` settles; a present group or EPERM (including pnpm's orphaned post-signal `ps` or a not-yet-reaped zombie) is observed again. Expiry fails closed: a present group stays unsettled with no failure, a final EPERM records `identity`, and other errors fail immediately. This is observation, never a command retry or signal. Fixture cleanup preserves primary and independent cleanup failures, retains uncertain paths and persists its issued observer/sentinel identities before fault injection.

Status and cancellation perform one authoritative terminal reread after confirmed owner absence, because terminal publication precedes owner exit but can race an earlier missing-file observation. This is not a command retry or inferred success: changed identity, missing/malformed evidence and unsettled results still fail closed. Duplicate and late cancellation preserve the actual terminal result. A single group signal can also be forwarded by real pnpm to its descendants; fixture signal observers remain registered until their actual effect and exit rather than assuming one raw signal delivery.

Cleanup assessment is read-only: it requires canonical browser driver and settled-producer identities, started-browser socket authority and strict invocation-descendant paths before reporting retirement. A legitimate never-started registration does not invent producer/socket identities. Live or uncertain producers, malformed journal/receipt evidence, failed exact inspections and nonempty owned inventories remain unconfirmed. A denied group observation preserves the original command exit/signal with an identity failure and unsettled scope rather than losing the terminal record. Actual output-file write failure records incomplete evidence and blocks partial-log delivery; complete-output fixtures also prove exact proxy transport with full, encoded, decoded and Basic credential forms excluded from both streams and receipts. Each shared-Engine `submitted` journal row from the test process's Docker CLI wrapper or the tracked Engine client's default submission carries a closed-set `call` label: transport `cli`/`http`, a fixed-vocabulary operation (CLI verb and known group subcommand, or HTTP method with an `{id}` endpoint template, otherwise `other`) and a caller basename (the issuing `*.test.ts` file from the call-time stack, else the tracked client's construction point; else the first non-wrapper `platform/test/` module; otherwise `unknown`), never arguments, names, IDs, queries or paths. Deployed-observer, binding/participant, browser exec and direct no-argument rows stay unlabelled; older unlabelled rows remain valid, any other label shape is malformed evidence, and labels never change settlement. When cleanup is unconfirmed because submissions stayed unsettled or kept a pending marker, the terminal `cleanup.unsettled` projection lists each distinct label with its count (at most 32 in journal order, `truncated` when more exist) and counts unlabelled rows, marker-only reservations and unattributable pending names under `unlabelled`; it carries no identifiers, arguments or paths, is absent when cleanup is confirmed, and never changes the verdict. Root cause stays UNKNOWN until the projection or other retained evidence names the call site.

## DSH browser runtime, images and verification-host prerequisites

The DSH browser lane (`pnpm test:docker`, `pnpm test:model`, `pnpm probe:dsh-api`, `pnpm probe:first-run`) requires trusted Linux amd64, a nonroot driver and the local default Docker daemon with ordinary UID mapping and support for `com.docker.network.bridge.gateway_mode_ipv4=isolated`. Rootless/userns Docker, remote Docker contexts and unqualified Docker Desktop namespace/Unix-socket sharing are unsupported, not reasons to fall back. `CHROME_BIN` must select the executable inside the complete pinned CfT140.0.7339.82 `chrome-headless-shell-linux64` distribution, not an arbitrary browser or PATH lookup. Root commands provision and qualify `images/browser-verification` once per invocation, outside navigation budgets, capture immutable image/Chrome identities, and provide Debian open-licensed CJK fonts without host font/library mounts or production-image changes.

Leave `DOCKER_HOST` and `DOCKER_CONTEXT` unset; the provisioner rejects these overrides rather than trusting a remote or differently scoped daemon. The custody `start` entrypoint rejects the same nonempty values before creating invocation state or sanitizing its child environment; silently dropping a caller-selected daemon is not admission.

Verification Docker CLI subprocesses accept only the optional uppercase `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` additions to their existing environment allowlists. Values remain exact (including empty strings); do not print them because proxy URLs may carry credentials. These are host verification inputs, not platform/Compose configuration. Docker daemon proxy configuration does not configure Buildx's client-side registry token exchange: supply the client inputs explicitly when needed. Invocation-owned `DOCKER_CONFIG`, existing PATH policy and local Engine restrictions remain unchanged. The host acquisition producer carries these inputs only to Docker descendants; native Chrome drops them and container creation does not inject them into isolated Chrome or employee instances. No proxy build arguments, TLS bypass, retries or implicit mirror changes are supplied.

Native user-image builds on giap-vps also depend on a verification-host egress prerequisite. Direct Debian egress (`deb.debian.org`) there measures about25KB/s on the host and in containers, against about1.2MB/s for `registry.npmjs.org` and about1.9MB/s through the host proxy. BuildKit `RUN` steps execute on the default bridge `docker0` (172.17.0.0/16) and never see the Docker CLI's proxy environment, and proxy build arguments and source rewrites remain forbidden (#313). The current `images/dsh-user/Dockerfile` and the stage-1 revision built by `volume-upgrade.docker.test.ts` share one base digest and one `apt-get` `RUN` line, hence one BuildKit layer; when that layer is not cached (it was found evicted at87% disk use), every native user-image build, including the stage-1 legacy image and the incompatible-range rejection build, exceeds its600s deadline. The operator-installed systemd oneshot `dsh-team-docker0-egress.service` therefore adds `ip rule priority 9500 from 172.17.0.0/16 lookup 2022`, so default-bridge sources use the routing table the host proxy's TUN auto-route maintains; it changes no proxy, dockerd or `daemon.json` configuration and supplies no build arguments, and it does not match the owned `198.18.0.0/15` test bridges or foreign bridges outside 172.17.0.0/16. When table2022 is absent the rule is a no-op and builds fall back to the slow direct path. This is host configuration owned by the operator: the code neither installs nor checks it.

The verification browser and production user-image builds retain their pinned bases' original official Debian bookworm/bookworm-updates and security sources. The user explicitly restored this policy in #313; the former source-rewrite helper and its `build-tools` context are removed from every live builder and example. Signed metadata/validity checks, archive keyring, suites/components, package lists, existing base references, DSH version and600s build deadlines remain intact. No mirror fallback, proxy build arguments, TLS bypass or runtime network-isolation changes are introduced.

## CI Docker evidence gate

After real execution and successful cleanup, trusted orchestration publishes sanitized durable evidence and the `dsh-team/docker` commit status as literal owner `DankerMu` on the reviewed PR head SHA, then reruns that head's CI. This read-only Docker-evidence lane uses `pnpm verify:docker-evidence`; missing, pending, failed, untrusted or other-SHA evidence fails immediately, with no polling or skipped success. Main squash pushes reuse evidence only from an associated merged PR with that exact merge SHA and identical pushed/head trees, reporting tree-equivalent reuse rather than a direct squash-SHA run. It has no self-hosted runner or VPS credential. The separately authorized model lane below executes through a one-shot restricted channel; neither lane permits `pull_request_target` or arbitrary PR remote execution.

Documentation-only diffs are exempt: when every changed path is Markdown outside `plugins/` and `images/` (plugin and image Markdown ships in images), the job logs the changed files and succeeds without reading evidence (`git diff --no-renames --name-only`). The PR range is `base...HEAD`; the main-push range is `before..after`. Renames count as delete plus add. Any other path or an empty diff keeps the evidence requirement; an unreadable range fails the job.

The gate requires `gh` plus `GITHUB_EVENT_NAME`, `GITHUB_REPOSITORY` and `GITHUB_EVENT_PATH`; GitHub Actions supplies these and a job-scoped read-only `GH_TOKEN`. Status and associated-PR pages are fully read under bounded process/output limits; malformed data, incomplete event context or failed API reads fail closed. The token belongs only to this verifier, never to tested Docker processes.

## Restricted real-model lane and browser rescue

# RAGFlow proxy

The single RAGFlow HTTP client and the instance-facing RAGFlow proxy under `/_platform/instance-api/ragflow/`.

Moved verbatim from the root `AGENTS.md`; normative behaviour lives in the OpenSpec specs (`openspec/specs/`, `openspec/changes/`). Keep this file current in the same change as the code it describes.

## Instance proxy

- The instance RAGFlow proxy lives under `/_platform/instance-api/ragflow/` (module `platform/src/ragflow-proxy/`); it declares exactly `GET version`, `GET datasets`, `GET datasets/{id}/documents` and `POST retrieval`. The prefix is a deliberate exception to the `/_platform/api/` Origin/JSON mutation guard: callers are employee instances, not browsers, and carry no platform session or Origin, so authentication is the Bearer instance token instead. A root `onRequest` hook authenticates every non-upgrade request whose router path (`routeOptions.url`, after find-my-way's `%XX` decoding) or raw path decoded the router's way (`routerPath` in `platform/src/request-path.ts`: truncated at the first `?` or `#`, absolute-form authority dropped, `decodeURI`d; `%2F` stays escaped, so `ragflow%2Fversion` is outside the prefix) starts with the prefix, before any handler runs: `Authorization` must be exactly `Bearer <64 lowercase hex>`, its SHA-256 must match `instance_token_hash` of a `running` row whose account is `active`, and the raw socket peer (normalized `::ffff:` form, never `X-Forwarded-For` or trusted-proxy resolution) must equal that row's `upstream_host`. Every rejection is the same401 with fixed logs; `published-loopback` mode rejects the whole prefix because its rows carry no instance address; a storage failure is a fixed500, never401. After authentication the request carries `instanceUserId`; undeclared paths and methods (including implicit HEAD, disabled with the per-route `exposeHeadRoute: false`) are404, upgrades stay the gateway's reserved-path404, and every proxy outcome is HTTP200 with a closed-set `{ result, … }` body. `GET datasets` sends one upstream `GET /api/v1/datasets?page=1&page_size=1001&orderby=create_time&desc=false` (RAGFlow rc2 has no `page_size` ceiling) and returns `{ result: 'ok', datasets: [{ id, name }] }` in creation order, nothing else; any query string on the instance request is `invalid-request` without an upstream call. The list is all-or-nothing: more than 1000 datasets, an entry count different from `total_datasets`, a malformed or duplicate entry, or an upstream body over 8MiB is `upstream-error`. RAGFlow repeats the owning account's avatar (`tenant_avatar`) and each dataset's own `avatar` as base64 on every row, so a large account avatar (about 100KB) breaks the list at roughly 80 datasets: do not give the RAGFlow account that owns the knowledge bases, or the datasets, large avatars (user decision 2026-11-03 to keep the 8MiB cap). `GET datasets/{id}/documents` requires a 32-lowercase-hex `id` and the query `page` (1..999999), `page_size` (1..100; RAGFlow rc2 silently resets larger values to10) and optional `keywords` (non-blank, at most256 UTF-8 bytes). The raw query is parsed and percent-decoded strictly before any settings read, so unknown, duplicate, malformed or `#`-bearing queries are `invalid-request`; the declared `params`/`querystring` schemas use `attachValidation: true` and only document the contract. `keywords` becomes rc2's unescaped `LIKE %kw%`, so `%`, `_` and `\` act as wildcards/escape. It returns one upstream page as `{ result: 'ok', total, documents: [{ id, name }] }` (`total` is the filtered count; a page past the end is `ok` with `[]`), validating every entry including that its `dataset_id` is the requested library; rc2 `code` 404/403 (library missing or invisible to the key) is `invalid-request`. Cross-page order is rc2's `create_time` without a tie-breaker, so consumers tolerate a repeated `id` across pages. The request log serializer replaces the query of every request under the prefix (same router/raw-path test as authentication), from the first `?` or `#`, with `?[redacted]`, so employee `keywords` never reach logs. The version route reads settings per request and returns `{ result: 'ok', version }` or `{ result }` with the connection-test limits; empty address or key is `not-configured` without an outbound request. `POST retrieval` requires a JSON media type (route `onRequest`, the same predicate as the platform mutation guard; otherwise the fixed415 before body parsing, after authentication), a 64KiB body (fixed413) and exactly `{ question, datasetIds }`, validated by hand before any settings read with Ajv disabled for that body: `question` non-blank by the same whitespace rule as `keywords` and at most4096 UTF-8 bytes (forwarded untrimmed); `datasetIds` 1..1000 distinct 32-hex IDs. Any other key, retrieval parameters (`top_k`, `page_size`, `similarity_threshold`, `rerank_id`, …) included, and unparseable or empty JSON are `invalid-request`; no error object is logged. It then reads settings once, preflights with the complete dataset list (`listRagflowDatasets`, whose failure is the result), drops IDs no longer listed into `excluded` (request order) and, only when some remain, sends one `POST /api/v1/retrieval` with exactly `question`, `dataset_ids` (the survivors), `page: 1`, `page_size: retrievalTopK`, `similarity_threshold`, `keywords_similarity_weight`, `rerank_id` only when non-empty, `rerank_candidates_count: max(64, retrievalTopK)` (rc2 rejects `page > candidates / page_size` by integer division, so values above64 would otherwise fail every retrieval) and `include_knowledge_compilation: false` (compiled rows carry no source file); never `top_k` or `vector_similarity_weight`. Each of the two upstream calls has its own `RAGFLOW_TIMEOUT_MS` (about20s worst case), and the response body is capped at8MiB. The answer is `{ result: 'ok', excluded, chunks: [{ content, documentName, datasetName, positions? }] }`, `{ result: 'no-results', excluded }` for zero chunks or an empty surviving scope (no retrieval sent), or `{ result }`; `datasetName` comes from the same preflight. Every chunk is validated and any chunk whose `dataset_id` is outside the searched set fails the whole answer as `upstream-error`. `positions` is emitted only as a non-empty array of5-number tuples, unmodified: rc2's tuple means `[page, left, right, top, bottom]` (1-based) for PDF but `[sheet, rowStart, rowEnd, colStart, colEnd]` for spreadsheets, so the proxy derives no page number. rc2 refuses a multi-dataset retrieval whose datasets use different embedding models (or mix with none) with `code: 102`, i.e. `upstream-error`; because a new Session selects every knowledge base, all knowledge bases must use one embedding model (user decision 2026-11-03). Real-bridge reachability from the instance's +2 address is proven by later stack/Docker tasks; loopback integration tests only simulate the address comparison.

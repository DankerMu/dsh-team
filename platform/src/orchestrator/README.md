## Subnets, transport and container lifecycle

- `PLATFORM_SUBNET_POOL` defaults to `172.30.0.0/16` only when absent. Supply a canonical dotted IPv4 network CIDR with zero host bits and prefix `/0` through `/28`, without whitespace. Operators must choose an address pool that does not conflict with host, LAN or existing Docker networks. After migration and before serving, startup compares its geometric `/28` capacity against persisted `maxRunningInstances` (default 60); equality passes, insufficient or malformed pools fail naming `PLATFORM_SUBNET_POOL`. The pool validation is geometric; the subsequent awaited owner reconciliation performs real Docker discovery.

- Task10.1 exposes pure `allocateSubnet(pool, occupiedSubnets)` through the orchestrator API: first-fit aligned `/28`, range-overlap exclusion, explicit exhaustion, no hidden reservation. Task10.2 (#45) must fetch fresh IPAM CIDRs from all relevant Docker networks, not only project-labeled networks, and serialize selection with creation. Repeating the same snapshot deliberately returns the same subnet; release/reuse is represented by the next snapshot. No network creation is supplied by task10.1.

- `PLATFORM_UPSTREAM_MODE` defaults to exact `network`; instances publish no host ports and the captured owner attaches the configured `PLATFORM_CONTAINER_NAME` (default `dsh-team-platform`) to each owned instance bridge. The inspected instance IPv4:3080 is the upstream. Platform identity and both endpoint inspect views are verified before use; name/ID changes, foreign endpoints, additional instance networks and publication fail closed. Retirement disconnects only that exact platform endpoint before deleting the confirmed empty bridge, preserving data and sibling/primary networks. Every instance bridge is an aligned `/28` with a fixed address layout (`instanceAddressLayout`): base+1 gateway, base+2 employee container, base+3 platform, base+4 reserved for the Document Server. Container creation declares base+2 through `IPAMConfig`, the first post-start validation verifies it, and a mismatch takes the started-container compensation (container and own bridge removed, both volumes kept, row `error`, `instance.start-failed`). The platform requests base+3 only when the employee endpoint is at base+2, and a declared platform address must equal base+3. Stage-1 instances created before the layout carry no `IPAMConfig`: they keep the (base, base+15) range check only, keep running until idle, administrator or disabled-account retirement, and are created at the layout on their next start. After platform recreation a survivor whose container is at base+2 is re-attached requesting base+3 and checked like any declared platform endpoint; one elsewhere is re-attached without a requested address and never checked against the layout.

- Readiness-failure cleanup can leave the exact indexed user container stopped and detached after deleting its bridge. Explicit retirement and indexed reconciliation may retire that retained error container only after immutable container/image/name/user and declared bridge-ID checks, no-publication validation, current-row/account fences and independent canonical-name/declared-ID absence confirmation. Missing live attachment is not a reason to reject this verified stopped state; live, foreign or extra attachments and unknown bridge endpoints still fail closed. No orphan discovery or reattachment is implied.

- Confirmed-started compensation revalidates the newly inspected post-stop document before deleting the container: immutable identity and stopped state, no publication, canonical stopped topology and the captured bridge declaration must still agree. A topology/declaration/publication change during stop preserves the stopped container and its endpoints with an explicit unconfirmed-compensation error; a pre-stop validation is not deletion authority.

- Explicit `published-loopback` is only for a platform process running directly on the Docker host. It creates the same labelled `/28` instance bridge and declares the employee container at base+2 with the same verification and compensation; instance 3080 is then published to 127.0.0.1 at a random host port and no platform or Document Server attachment occurs, so the knowledge-base proxy and Office editing delivered by later stage-2 groups are unavailable in that mode by design (stage-2 design decision 2). Retirement applies the same declared-bridge fence, pre-deletion endpoint-ownership capture and empty-bridge deletion in both modes. It does not satisfy the deployment no-host-port requirement. Both configuration fields are validated before reconciliation/listening; every lifecycle operation uses the owner's captured transport.

- Task10.4 (#47) extends explicit awaited `owner.reconcile()`: after platform recreation, a fresh owner resolves the configured name to the new immutable ID; a live owner never resets its pin. Only missing configured-platform membership on an otherwise verified active, running, unexpired indexed survivor is repaired, with fresh identity/topology/upstream and complete row/account fences before acceptance. Successful recovery preserves containers, credentials, rows and audits. Confirmed attachment failure uses guarded retirement and atomically records safe `error`/null runtime identity with the existing error-reason stop audit; repeated stop/reconcile preserve that terminal error, and fresh start may retry. Unknown or changed resources and failed cleanup remain explicit failures, not successful retirement evidence.

- Reconciliation may delete exact canonical labelled bridge `/28` orphan candidates, including those without an account/index, only after fresh exact404 absence of both canonical and any distinct indexed user container, unchanged row/account and captured network identity/subnet, and freshly verified empty or configured-platform-only endpoints. It disconnects only the verified platform endpoint with `Force:false`, confirms emptiness and exact-ID deletion, and preserves data, sibling/primary networks and unrelated resources. Cleanup uses the existing per-user queue, respects owner-local unknown-create quarantine and failed indexed reconciliation, and retains bounded submitted-mutation settlement despite cancellation. Published-loopback performs no platform attachment; neither mode uses global prune.

## Instance service

- Task12.1 supplies one process-lifetime instance service in the orchestrator context. Main creates the real Docker client/service and awaits reconciliation before listening; startup failures do not serve traffic. Authenticated `POST /_platform/api/instance/start` accepts only an empty JSON object and is the sole employee startup trigger. Authorization is rechecked after body processing. GET `/_platform/api/instance` and gateway HTTP/WebSocket resolution only observe. Both API success responses contain exactly `{status, reason}` (running has null reason; other states carry their machine code), never backend credentials, endpoints or diagnostics; ordinary states return200, unexpected failures sanitized500. Offline app construction still declares both routes/auth/schemas but authenticated calls return sanitized503 without external lifecycle work.

- Each admitted start snapshots canonical stored model settings and injects the key only as `DSH_TEAM_MODEL_API_KEY` through the existing managed composition/start path. Same-user calls reuse one startup-to-readiness flight; readiness performs credential acquisition once. API status observes current rows and owner pending capacity, not a separate reservation ledger or cached last outcome. Gateway requires a complete running endpoint/cookie from one current row and continues routing existing valid instances if model settings later become incomplete. App shutdown closes service admission, settles owned work and actual owner queue tails before closing SQLite; a disconnected HTTP caller does not cancel that shared instance work. Real Docker acceptance registers and logs in over HTTP, explicitly starts, polls authenticated readiness, verifies real DSH HTML and same-container repeat startup without a provider request.

- When startup/readiness fails without a durable error transition, the service retains only an identity-fenced exceptional-work receipt (container/start identity or explicit no-row identity, no endpoint/credential/diagnostic). Matching observations fail safely rather than silently reporting stopped or indefinitely starting. A changed durable identity/state invalidates the receipt; explicit new admission clears ordinary failure receipts, but cannot resurrect an unchanged verified-absent running identity without verified reuse. It is not a lifecycle-state cache or admission counter. Persisted error remains an ordinary200 machine state.

- Exact indexed-container404 plus unchanged account/instance snapshot emits the owner's typed verified-absence observation before replacement image/composition work. Only that matching old identity becomes pending/non-routable; a failed replacement retains the exceptional receipt even for a formerly running row. Gateway and status use the same observation. Generic inspect failures do not invalidate healthy running reuse, and different replacement/sibling identities remain independent.

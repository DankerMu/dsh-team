# Managed overlay

How `generate.ts` composes the per-instance managed `cordis.patch.yml`.

Moved verbatim from the root `AGENTS.md`; normative behaviour lives in the OpenSpec specs (`openspec/specs/`, `openspec/changes/`). Keep this file current in the same change as the code it describes.

## Generator inputs and rows

- The managed overlay generator (`platform/src/managed-config/generate.ts`) takes `webToolsEnabled`, `pluginRegistries`, `registryProbeEnabled` and the `catalogStates` projection as required pure inputs; the orchestrator reads the catalog once at construction with the same `readPluginCatalog()` the admin routes use and reads the four settings at each start. It always writes `{ id: 'plugin-manager', config: { registry: <first>, fallbackRegistries: <rest> } }` and `{ id: 'ui-plugin-manager', config: { registryProbeEnabled } }` (both upstream rows carry no `config`, so whole-config replacement loses nothing; values are not normalised). It also takes the required `platformPort` (the orchestrator passes `PLATFORM_PORT` in `network` mode and `null` in `published-loopback`): a port adds exactly `{ id: 'knowledge-base', config: { platformUrl: 'http://<instance +3>:<port>' } }` after the catalog rows, identical in all three catalog states (an absent target only warns), with no RAGFlow address, key or retrieval parameter; `null` adds nothing. The address is reachable only while the platform container listens on all its addresses (Compose sets `PLATFORM_HOST=0.0.0.0`), and a running instance keeps the port it started with until its next start. Catalog rows follow the locale rows in catalog order: a `required` entry must be `forced-on` (else `TypeError`) and keeps its existing activation rows; `employee` writes nothing; for a manageable bundle the composition reader loads the canonical `/opt/dsh-team/<id>/cordis.patch.yml` and reports whether its inserted rows are present (mixed presence is an invalid composition). `forced-on` writes `{ id, disabled: false }` per inserted id when present and the whole canonical patch (presets web-tool-filtered) when absent; `forced-off` writes `{ id, disabled: true }` per inserted id, drops those presets from the whole-row emission and restores `agent-preset-registry` to DSH's release default `standard` (a bundle override of any other row, or a forced state on a bundle with an empty patch, is a `TypeError`). The overlay still cannot change the plugin page's `enabled` checkbox, which is `dsh.profile.bundles` membership; the `platform-nav` client instead hides a forced bundle's native switch and shows a locked state equal to the overlay's forced state (#509). Residuals: the install wizard and update path still call `setBundleEnabled`, row-level switches on a forced bundle's detail page stay movable without effect, and the card's `data-plugin-status` still reflects profile membership. Accepted residuals: re-checking an overlay-inserted bundle at runtime duplicates its ids until the next start; unchecking a forced-on bundle that was present at start drops its presets until the next start; a natively uninstalled forced-on bundle loses the profile copy its `!!js` skill path resolves against; `forced-off` rewrites `agent-preset-registry` to `default: standard`, discarding an employee or third-party default; an image update that changes a forced-state bundle's inserted ids fails that employee's start at `managed composition` until the administrator resets their profile. Registry URLs are written verbatim into the 0444 overlay that the instance bind-mounts read-only and DSH returns them to the employee's plugin page, so a credential inside a registry URL is readable by every employee, like the shared model key; prefer credential-free intranet mirrors. The explicit `registry` replaces the profile `.npmrc` fallback DSH used before, so an existing offline deployment must save its intranet mirror and probe-off through `PUT /_platform/api/admin/plugin-sources` right after upgrading (on the administrator page `/_platform/admin/plugins`).

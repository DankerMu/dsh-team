# Managed overlay

How `generate.ts` composes the per-instance managed `cordis.patch.yml`.

Moved verbatim from the root `AGENTS.md`; normative behaviour lives in the OpenSpec specs (`openspec/specs/`, `openspec/changes/`). Keep this file current in the same change as the code it describes.

## Generator inputs and rows

- The managed overlay generator (`platform/src/managed-config/generate.ts`) takes `webToolsEnabled`, `pluginRegistries`, `registryProbeEnabled` and the `catalogStates` projection as required pure inputs; the orchestrator reads the catalog once at construction with the same `readPluginCatalog()` the admin routes use and reads the four settings at each start. It always writes `{ id: 'plugin-manager', config: { registry: <first>, fallbackRegistries: <rest> } }` and `{ id: 'ui-plugin-manager', config: { registryProbeEnabled } }` (both upstream rows carry no `config`, so whole-config replacement loses nothing; values are not normalised). It also takes the required `platformPort` (the orchestrator passes `PLATFORM_PORT` in `network` mode and `null` in `published-loopback`): a port adds exactly `{ id: 'knowledge-base', config: { platformUrl: 'http://<instance +3>:<port>' } }` after the catalog rows, identical in all three catalog states (an absent target only warns), with no RAGFlow address, key or retrieval parameter; `null` adds nothing. The address is reachable only while the platform container listens on all its addresses (Compose sets `PLATFORM_HOST=0.0.0.0`), and a running instance keeps the port it started with until its next start. Catalog rows follow the locale rows in catalog order: a `required` entry must be `forced-on` (else `TypeError`) and keeps its existing activation rows; `employee` writes nothing; for a manageable bundle the composition reader loads the canonical `/opt/dsh-team/<id>/cordis.patch.yml` and reports whether its inserted rows are present (mixed presence is an invalid composition). `forced-on` writes `{ id, disabled: false }` per inserted id when present and the whole canonical patch (presets web-tool-filtered) when absent; `forced-off` writes `{ id, disabled: true }` per inserted id, drops those presets from the whole-row emission and restores `agent-preset-registry` to DSH's release default `standard` (a bundle override of any other row, or a forced state on a bundle with an empty patch, is a `TypeError`). The overlay still cannot change the plugin page's `enabled` checkbox, which is `dsh.profile.bundles` membership; the `platform-nav` client instead hides a forced bundle's native switch and shows a locked state equal to the overlay's forced state (#509). Residuals: the install wizard and update path still call `setBundleEnabled`, row-level switches on a forced bundle's detail page stay movable without effect, and the card's `data-plugin-status` still reflects profile membership. Accepted residuals: re-checking an overlay-inserted bundle at runtime duplicates its ids until the next start; unchecking a forced-on bundle that was present at start drops its presets until the next start; a natively uninstalled forced-on bundle loses the profile copy its `!!js` skill path resolves against; `forced-off` rewrites `agent-preset-registry` to `default: standard`, discarding an employee or third-party default; an image update that changes a forced-state bundle's inserted ids fails that employee's start at `managed composition` until the administrator resets their profile. Registry URLs are written verbatim into the 0444 overlay that the instance bind-mounts read-only and DSH returns them to the employee's plugin page, so a credential inside a registry URL is readable by every employee, like the shared model key; prefer credential-free intranet mirrors. The explicit `registry` replaces the profile `.npmrc` fallback DSH used before, so an existing offline deployment must save its intranet mirror and probe-off through `PUT /_platform/api/admin/plugin-sources` right after upgrading (on the administrator page `/_platform/admin/plugins`).

## Instance address, retained rows and the isolated credential store

DSH0.2.1 binds only the concrete IP literal its overlay names and rejects `0.0.0.0` during configuration validation. The orchestrator therefore generates the managed overlay after network allocation with `webserver.host` set to the instance's base+2 address; generation throws unless that value is a canonical dotted IPv4, not `0.0.0.0`, with a last octet of 2 modulo 16. Inside the instance, port3080 answers only at the base+2 address, never at the container's own loopback: the network and isolation Docker cases use that as their positive control, and the stage-1 survivor reconcile case emulates a `0.0.0.0`-bound survivor by rebinding the moved container's overlay to its new address and re-acquiring the cookie. Readiness extracts the launch token only from a complete stdout line `dsh web: http://<base+2>:3080/?token=<43 base64url characters>`; lines naming any other address never yield a token. Every Docker fixture that runs real DSH Web (`platform/test/web-startup-fixture.ts`) and both DSH browser probes (`scripts/probe-dsh-api-lifecycle.sh`) create invocation-owned, `dsh-team.test-run`-labelled `/28` bridges chosen from `198.18.0.0/15` by the orchestrator's `allocateSubnet`, start each Web container at its bridge's base+2 address with loopback-only publication, and remove containers before networks. The occupied set merges a fresh IPAM snapshot of every Docker network with the host IPv4 kernel routes from `/proc/net/route` (the probes read `${PROBE_ROUTE_TABLE:-/proc/net/route}`), converted by the shared `hostRouteCidrs` with the default route skipped. Reason: giap-vps routes `198.18.0.0/30` to the local proxy tun `Meta`; an IPAM-only snapshot placed the first `/28` on it and every host publication probe to `198.18.0.2:3080` went unanswered. A missing or malformed route table, pool exhaustion and a network-creation conflict fail explicitly, with no other pool and no retry. The wildcard-rejection case starts the user image on its own bridge with a handwritten `host: 0.0.0.0` overlay and requires a nonzero exit within60s with no `dsh web: http` line; logs are judged in memory and never written or printed.

The managed overlay retains every row DSH0.2.1 adds, including the preset `tool-plugin-market` row: its `plugin_market` tool only lists indexes and bundles, depends on a `pluginMarket` service that neither the Web profile nor `dsh-base` mounts, and requests only configured index sources (default `indexes: []`). Whether it stays belongs with the Discover page and plugin-source management, not the network-tool removal, which removes only `@deepseek-ai/dsh-tool-web` and only while `webToolsEnabled` is `false`.

F18 credential priority uses an isolated credentials store. The generated overlay gives the managed `llm-pi-ai` row `isolate: { credentials: 'dsh-team-platform' }` and inserts, after `platform-nav` and before the final `agent-loop` row, `dsh-team-platform-credentials` (`@deepseek-ai/dsh-credentials-local`, the same isolate label, `path: /opt/dsh-team/credentials/platform.yaml`, `dshHome: /data/home`, `watch: false`). The image creates `/opt/dsh-team/credentials` as an empty root-owned0555 directory, so that store file never exists: uid1001 can traverse and `opendir` it but cannot create files, and the managed provider's `apiKeyEnv` resolves from the platform-injected process environment rather than the employee's global `.credentials.yaml`. The user-image case asserts the directory's ownership, mode, `opendir` success and `EACCES` on write. The credential-priority Docker case writes an employee `.credentials.yaml` entry with a different nonsecret value for the managed reference, restarts the instance over the same volumes, completes one turn against a test-owned in-container endpoint and requires exactly one request whose Authorization SHA-256 matches the platform value; only hashes are retained. It also rejects the restarted instance if its logs contain `Failed plugins (`, `plugin tree failed to load`, `dsh: skipping profile bundle`, `dsh: disabling profile plugin` or `did not activate` (an entry outside DSH's required startup set, such as `dsh-team-platform-credentials`, that fails or stays pending is only warned about as `dsh: warning: N entr(y|ies) did not activate` and DSH keeps booting): without the realm's credentials service pi-ai falls back to the launch environment, so a failed isolated store would otherwise pass with the platform value. `client-connection` still writes browser-session secrets to the global store, and employee settings-page edits of `llm-pi-ai` are still replaced by the whole managed config. Accepted residual risks, documented only and not covered by that case: any layer that can write patch rows, including the employee-writable `$DSH_HOME/cordis.patch.yml`, can join the same `isolate` label and mount another `credentials` implementation in that realm (employees cannot remove the platform's `isolate`); a missing platform variable falls back to `.env` (the platform always injects it); the settings page still describes the global store's credential state (display only); pi-ai OAuth login fails because the store is unwritable (this project does not use it). The shared model key remains readable inside the instance.

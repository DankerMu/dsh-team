# Verification suites

What the integration, Docker, model and local-stack suites under `platform/test/` prove, their host prerequisites and evidence rules.

Moved verbatim from the root `AGENTS.md`; normative behaviour lives in the OpenSpec specs (`openspec/specs/`, `openspec/changes/`). Keep this file current in the same change as the code it describes.

## Platform UI fixture

The UI fixture retains one public loopback TCP listener continuously from Origin selection through teardown. After the real Fastify app binds its own ephemeral loopback listener through the normal lifecycle, the canonical verification byte relay activates that backend exactly once; only then are API/browser consumers admitted. This is an explicit verification-only TCP hop, not direct browser binding to Fastify and not an HTTP proxy: Host, Origin, cookies, HTTP/WebSocket bytes and the real loopback source peer retain their existing semantics. Pre-ready connections close without buffering; no released-port reservation, shared fixed port or listen retry is used. The same relay implementation serves the isolated browser lane and is shipped in its build/rescue module closures.

UI fixture teardown fences its public relay before upstream retirement, attempts independent API/app cleanup even after a failure, and preserves the original scenario error with secondary cleanup errors. Multiple cleanup failures are also aggregated when the scenario succeeds; a lone error retains its identity. The application retains service-before-SQLite drainage; uncertain lifecycle work is not hidden by closing its database. Failed cleanup retains the private directory rather than deleting evidence or claiming full retirement. Process-boundary regressions exercise early/initialized/use port exclusion, real Origin policy, pre-ready sockets, normal/setup/callback failure settlement and an unrelated listener; existing browser error observers remain unchanged.

## Docker suite cases

The resource-OOM verification also requires trusted host read-only kernel-journal access through noninteractive `/usr/bin/sudo -n /usr/bin/journalctl` on the current boot. The fallback queries only the exact owned systemd Docker `oom_memcg` and the physical-pressure time window, with a 5s process deadline and 64KiB output cap; records are projected to typed causal fields, never raw journal messages/errors. Missing privileges/records or malformed, global, foreign or out-of-window evidence cannot substitute for OOM proof. This is a verification-host prerequisite, not a production dependency or permission to modify host controls; Docker OOM flags and child cgroup-counter proof remain valid paths.

The Docker suite builds the user-image Dockerfile with the `images/dsh-user` primary directory context and explicit BuildKit named contexts `zh-locale=<repo>/plugins/zh-locale`, `permission-tiers=<repo>/plugins/permission-tiers`, `office-agents=<repo>/plugins/office-agents`, `platform-nav=<repo>/plugins/platform-nav` `knowledge-base=<repo>/plugins/knowledge-base` and `office-hints=<repo>/plugins/office-hints` (no repository-root files or secrets), and runs each probe from its captured image ID.

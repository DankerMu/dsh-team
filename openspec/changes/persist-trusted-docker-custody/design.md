# Design

## Context

See proposal.md for motivation. The existing full root command already owns browser provisioning, canonical rescue and original Vitest discovery. Its final exit includes those checks, but SSH currently carries the only complete output/verdict. The model lane's detached-owner pattern, atomic receipt writer and process-birth helpers exist; its authorization, secret handling and worker command are not reusable as a Docker lane.

An owned Linux experiment using pinned real pnpm showed that signalling only pnpm did not settle its child. A separate session/group with birth-checked group SIGINT reached the literal child. This is process-primitive evidence only: it does not establish Docker mutation settlement or safe acquisition cleanup.

## Goals / Non-Goals

The governing invariant is one reviewed invocation, one durable owner and an honest terminal outcome: observer loss cannot manufacture completion, and successful cleanup cannot turn command failure into acceptance.

Non-goals: automatic provider calls, GitHub status publication, restricted-model owner changes, image/proxy policy changes, new global execution deadlines, deadline increases, retries, test selection changes, global/PID-prefix rescue, general host watchdog or automatic recovery after unknown owner death. The trusted parent still performs independent host/resource verification before attestation.

## Decisions

### Narrow independent owner rather than a second model service

Use a remote POSIX detached Node owner with private stdio, following the existing detached-owner pattern without its model authorization. The root command exposes start, status, logs and explicit cancel operations. The prepared dedicated checkout must match the supplied full reviewed SHA and remain frozen; the owner records its canonical root identity and rechecks admission before work. Start does not install dependencies, build unrelated artifacts or fetch a different revision.

The owner has its own session; the original `pnpm test:docker` child has a separate owned session/group. SSH clients only observe. Qualification must actually disconnect SSH while the child is live and then reconnect to the same owner/result on giap-vps. No silent fallback is permitted if that host cannot sustain the detached owner. A transient-service topology was considered but adds service/environment custody without being required by this SSH-disconnection contract; extending the model owner would violate the lane boundary.

### Publish authority before work

Create a unique private invocation directory and intent, then publish the owner's PID plus canonical birth identity, reviewed SHA, exact argv and canonical checkout identity before spawning test work. Capture the child identity separately. UUID-only public operations resolve within the fixed private custody root; validate file type, ownership, permissions, bounds and matching identities. Reuse the atomic receipt writer, but not its browser-specific reader for unrelated schemas. A dead owner without a valid terminal receipt is unknown, never completed or available for PID-only takeover.

Use an invocation-owned short temporary root and private Docker configuration, with the existing pre-create resource journal. Keep launch records, output and terminal receipts outside writable browser profiles. Do not persist environment values. No CI/model invocation marker is introduced for ordinary Docker work.

### Safe complete output without whole-run buffering

Capture stdout and stderr incrementally into separate private files, preserving each stream's order and backpressure. Explicitly allow only required runtime/tool fields and existing ordinary proxy inputs into the test environment; never inherit provider/GitHub/SSH credentials. Preserve proxy strings at the existing Docker boundary, but exclude their values and credential components from durable output even across chunk boundaries. Existing inner command output bounds remain unchanged. Output loss or write failure is explicit and prevents acceptance; it is not a truncated successful transcript. Final receipts bind completed logs by byte count and digest.

### Cancellation is an owned transition, not observer timeout

A validated cancel operation publishes an invocation/owner-bound request; the owner alone signals its captured child group after fresh birth/identity checks. Observing-client loss does not create that request. Never assume a signal to pnpm alone forwards to its descendants. If the child identity changed or work is already terminal, do not signal a guessed group. Preserve original command exit/signal independently from the cancellation request.

Group interruption can leave daemon-side creation uncertain. Settle the actual command and its owned process scope before cleanup assessment; canonical browser producer/receipt uncertainty remains authoritative. Unknown work or identity means unconfirmed cleanup and retained evidence, not broad rescue. The owner does not add a second Docker deletion implementation or kill unrelated processes to make cleanup pass.

### Separate command, evidence and cleanup outcomes

The recorded command result is the original root command's actual exit/signal, not an invented independent Vitest verdict. Record interruption and output completeness separately. Assess registered Docker targets and browser/image receipts through existing exact-absence/identity contracts after process settlement; discovery never grants deletion authority. Existing root-command cleanup remains the mutation owner. Missing/malformed authority, surviving work or resources is unconfirmed cleanup. Command failure plus observed cleanup remains failure; command success with incomplete output or cleanup is not acceptance.

Retain private evidence needed for reconnect and diagnosis, including failures. The parent independently confirms owned retirement and unchanged daemon/bridge/unrelated workloads before any GitHub success status.

### Complete mutation observation without production instrumentation

The producer inventory includes ordinary host CLI, test-process Docker HTTP, browser auxiliary CLI/acquisition, deployed-platform shared-Engine HTTP and invocation-private Engine work. Track actual external submissions, not merely logical command names. A test-owned non-Docker stop executable must retain the original timeout/kill/close oracle without inventing a Docker submission. Never settle an actual uncertain request because its test expected failure. Reuse browser acquisition receipts and exact private-Engine retirement authority rather than pretending either proves shared-daemon settlement.

One canonical verification-only tracker publishes before dispatch and refuses dispatch if publication fails. Fulfilled canonical Docker JSON calls retain their full-body/parse boundary; transport loss, malformed responses and failed completion publication remain unresolved. GET/HEAD and exact `POST /containers/<target>/wait` are observations, including failed/cancelled waits; other operations are tracked conservatively. Per-request records contain opaque identities and fixed states only, never arguments, request/response bodies, credentials or raw exceptions.

Completion publication uses a pending marker as a conservative fence within that same canonical submission protocol, not a second ledger. Durably create the exact attempt's private marker before dispatch and publish its submitted record. On qualified completion, write the accepted outcome record, fsync it and successfully close its descriptor before removing only that marker. Ordinary operations require a settled row; the separately authorized contained-exec case below may publish a client-closed/operation-unknown record without claiming daemon settlement. No further fallible positive-publication step follows removal. Assessment after independent writer retirement requires valid operation-specific evidence and no pending publication markers; absent, replaced, foreign, malformed or unreadable marker authority fails closed. A visible outcome row after failed fsync/close is insufficient because its marker remains. Death before removal is conservatively unconfirmed; resurrection of a removed marker after a crash also only causes conservative rejection. Do not claim arbitrary filesystem/power-loss durability beyond these ordered primitives.

A successful operation with failed completion publication rejects with that evidence failure. A qualified original Docker rejection retains the exact original error object while the retained marker independently makes custody unconfirmed, including in a fresh assessor process. Later successful requests cannot erase an earlier marker. Marker creation failure prevents dispatch; marker-removal failure retains conservative uncertainty. Marker/journal identity is bound to the captured invocation, and writable deployment mounts expose only this evidence storage, never owner logs, proxy configuration or other secrets.

The user additionally authorized one declared CLI exit for the resource-OOM pressure exec. Its caller passes `acceptedStatus=137` to the canonical synchronous `runDockerCommand`; only a normally exited CLI with exactly that status, no spawn error and no signal may publish the ordinary settled row, because the daemon answered the exec with that exit code. The fixture's independent wait/inspect/cgroup/kernel-journal OOM proof remains mandatory. Undeclared nonzero exits, other statuses, signals, spawn errors and lost responses stay pending; callers without a declaration keep identical behavior.

The following rejection matrix is exhaustive for this repair. `<target>` is one canonical nonempty Docker identity/name segment, not a dot-segment, encoded separator or extra path; existing query parameters are forwarded unchanged and are not treated as another endpoint.

| Method and endpoint                                                        | Status | Authoritative observation and meaning                                                                                                                                             |
| -------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /networks/create`                                                    | 403    | The original canonical `DockerHttpError` observed at response headers rejects this network-create submission, including the existing overlap control.                             |
| `POST /containers/<target>/stop`                                           | 304    | The original canonical header rejection reports no stop transition for this request; original independent stopped-state/identity checks remain required.                          |
| `DELETE /containers/<target>`, `/networks/<target>` or `/volumes/<target>` | 404    | The original canonical header rejection reports this exact delete target absent; it does not settle any earlier create, remove another pending entry or confer cleanup authority. |

These outcomes may complete only their own submission while rethrowing the same error object. They do not require consuming an error body that the unchanged client already destroys. All nonmatching method/path/status combinations, structurally similar noncanonical errors, transport failures and malformed/truncated successful responses remain unresolved. CLI stderr/status cannot borrow this HTTP matrix. Real Unix HTTP controls must prove each permitted pair and negative sibling endpoints/statuses, original errors and resource-state checks.

### Isolated-browser exec: tracked outcome and retired capability

The user selected “接受执行能力退役证明” for the existing browser rescue controls. The active protocol exec may reject when its exact browser container is removed, and another exec against that already-retired ID must still reject. Both remain tracked submissions. Their local CLI outcomes and unknown daemon-operation outcome are retained; no expected test failure, stderr text or generic nonzero exit completes an ordinary mutation.

Before spawning, bind a narrowly typed browser-exec submission to the invocation, canonical private browser receipt, its nonce/image/producer authority and full immutable container ID. Migrate the id-only helper/callers without a compatibility alias. Reject name-only, foreign, missing or changed authority and preserve the fixed unprivileged `docker exec <exact-id> node -e <source>` shape and existing isolated-browser confinement. Do not persist source text, arguments, output or credentials. A normally settled exec can retain ordinary completion; a failed/unknown exec must retain its original rejection.

For failed/unknown exec, wait for the actual issued CLI child's `close`, including timeout, output-limit and progress-callback failure paths, before publishing a distinct client-closed/operation-unknown record. Use the same write/fsync/close/pending-marker fence; removing its publication marker proves only that these outcome facts were published, not operation settlement. Missing or failed publication remains unconfirmed. The ordinary strict submission checker still rejects this unknown outcome.

Only the final read-only custody assessor may additionally recognize execution capability as retired, after independent host-writer retirement and all of: unchanged captured browser authority, settled original acquisition producer and retired driver, canonical ownership-checked container retirement, and fresh authoritative absence of that exact immutable container ID. Reuse the canonical browser validator/retirement evidence rather than inventing cleanup. It must project `operationOutcome: unknown` and `executionCapability: retired` distinctly in durable terminal evidence. It must not rewrite the journal to “settled” or delete pending markers. A live target, failed exact inspection/removal, unknown producer/client closure or substituted authority remains unconfirmed.

Keep the terminal projection bounded: every cleanup result carries `browserExec`, null when no unknown exec has qualified retirement, otherwise `{ operationOutcome: 'unknown', executionCapability: 'retired', submissions, sha256 }`. `submissions` is the positive safe-integer count of unique original submission IDs; `sha256` binds their sorted canonical JSON array. Full attempt identities/outcomes remain in the canonical submission records, not a duplicate terminal journal. Only confirmed cleanup may carry the non-null projection. Migrate terminal writers/readers and reject missing/malformed fields without a legacy-record shim. A successful negative scenario may preserve unknown exec outcome while its original root suite passes; retirement never changes that suite's actual exit/signal or the existing passing-outcome predicate.

This is not evidence that Docker acknowledged the original exec request. The removed immutable target cannot execute a late exec or redirect it into a replacement container. The proof applies only to this captured, confined browser execution capability; it cannot justify create/build/network settlement, arbitrary CLI errors, missing receipts, ordinary publication failures or weaker cleanup authority. Keep the original real rescue/stream/rejection assertions and a genuinely submitted lost-response mutation negative control.

### Verification-only deployed client observation

The user selected “允许验证专用观测”: invocation-only startup injection and private mounts may observe the deployed platform. Production source, production images, formal `deploy/compose.yml`, Docker socket routing and employee/browser configuration do not change. Status quo would leave full cleanup unsupported; a socket proxy is forbidden. Patching `node:http` events is rejected because it risks stream-flow changes and cannot observe canonical JSON validation.

Use a Node24 test-only `--import` preload with synchronous module hooks. Intercept only the exact compiled orchestrator client module and delegate to its unchanged original bytes through an internal bypass URL. Re-export original symbols and error-class identity while wrapping the original `createDockerClient` with the same canonical verification tracker used by host fixtures. Preserve factory/request arguments, values, error identity, signals, byte bounds and log streams. Do not rewrite production source text, consume HTTP streams or inherit `NODE_OPTIONS` into CLI/browser/employee children. Missing or incompatible module interception is an evidence failure, never an unobserved fallback.

Separate stable container authority from process-incarnation generation. The parent reserves a fresh participant before every initial start, same-ID restart or replacement start. Each immutable capability binds invocation, unique generation nonce, expected module/socket and exact journal identity; its narrow completion capability can complete only that participant. The invocation-generated Compose override uses a stable per-container authority label, bootstrap command and readonly capability directory, plus readonly observer closure/anchor and private writable evidence storage. The parent atomically publishes a current-generation manifest inside that directory; an individual file bind is not used for the replaceable manifest. The child captures its generation once and never rereads the manifest to adopt a successor. No new socket mount or proxy is introduced; existing labels retain deletion authority.

After each start the parent independently verifies the container ID, image, stable authority label, command and observation mounts, and binds the fresh generation to its actual StartedAt/process incarnation. The preload initializes only when the exact factory is wrapped; malformed or foreign capabilities fail before Docker work. Before parent binding is available, every request still publishes under the already reserved generation before dispatch, and the participant remains unconfirmed until binding is verified. Do not add a bootstrap wait, retry or timeout to hide this interval. Only that initialized and bound generation's normal exit may complete its participant. Request uncertainty survives process exit and resource deletion; final assessment independently establishes writer/container retirement.

Preserve the existing audit's same-container `stop --time 30` with45s command budget, exit0 check and exact-ID `start`, including the `restarted` witness and timeout/no-start oracle. After the original stop completes and that exact container is independently verified stopped, publish a fresh generation before the unchanged start command; require a new process incarnation without recreating the container or clearing predecessor uncertainty. Genuine platform recreation still drains and retires the old ID and creates new container authority plus a fresh generation. Retain all old capabilities/claims/evidence; replay, already-live admission, failed starts and missing incarnation binding remain unconfirmed. The journal stays0600 and its directory0700; writable mounts expose only evidence storage to the uid1000 platform, never employee containers or owner logs/secrets. Unknown evidence must survive the ordinary user-image fixture's config-directory cleanup.

The canonical reservation/initialization/completion protocol must reject replay, duplicate completion, changed journal identity and cross-generation capability use. Partial publication, abrupt process death and missing preload remain unconfirmed. The observer dependency closure must be copied atomically into all selected build/rescue fixtures. Only necessary inert helper COPY/build-context updates to the existing verification-browser image are permitted: no base/runtime/library/version or browser configuration change, no production image change, and no forwarding custody environment or host credentials into isolated Chrome or the restricted-model lane. This allowance grants no remote build execution.

### Verification order and containment for the final repair

1. Preserve the existing final fix pass2/2 and original RED evidence. The raw HTTP volume tracer already proves that a persisted stalled create remains unresolved after exact cleanup; qualify positive settlement and precise rejection controls before migrating sibling callers.
2. Qualify the actual compiled-client module seam on pinned Node24 before adopting it. The owned pilot rejects missing preload, intercepts the public/re-exported factory, preserves error-class and JSON effects, and leaves compiled bytes and `node:http` unchanged; it does not prove deployed custody.
3. Review this revised fixture, then implement the canonical tracker/transport seam, per-generation capability and deployment override in one consolidated repair. Use actual Unix HTTP and child-process cases for lost responses, publication failure, missing hook/factory, abnormal exit, recreation/replay and no credential leakage.
4. Run affected local regressions, selective closure/import checks and actual outside-runner smokes. Then review the whole candidate and perform the original exact-head full Docker/disconnect/reconnect plus standalone Compose with independent retirement. Current shared-host build uncertainty remains a runtime prerequisite, not permission to retry or weaken gates.

Rollback removes only the invocation-generated override/mounts through existing exact-owned cleanup after writer retirement; retain uncertain evidence. Revisit the seam if Node's module-hook API, compiled module identity/export shape, Docker endpoint semantics or deployment startup entrypoint changes. No compatibility shim or second ledger implementation is retained.

## Verification and Delivery

Use real owned Node/pnpm subprocess fixtures behind external process boundaries, not mocks of custody logic. Trace one behavioral RED/GREEN slice at a time: durable output, launch/status, disconnect, cancellation and identity refusal, then cleanup/evidence failures. Tests must preserve nonzero results, prove no secret canary persistence and preserve an unrelated live sentinel. Real giap-vps qualification disconnects an observer during live work, reconnects by UUID, and runs the delivered entrypoint through the original complete Docker suite. Standalone Compose and independent cleanup/host fences remain separate required evidence.

## Risks / Trade-offs

- Detached process survival depends on the qualified host's session policy; real SSH-disconnection evidence is required, and missing owner/final evidence fails closed.
- PID reuse or child-group loss must not authorize signalling; require captured birth and invocation ownership, and refuse uncertain identity.
- Full logs consume disk; streaming/backpressure avoids memory growth, while write failure invalidates evidence instead of silently dropping output.
- Canonical root cleanup can remain unconfirmed after interrupted creation; preserve that failure and authority rather than inventing rescue guarantees.
- A frozen checkout is an operator precondition, not a defence against a malicious same-UID operator rewriting the reviewed tree during execution.

## Migration and Containment

Document the delivered custody command as the ordinary trusted full-Docker remote entrypoint, retaining the original test command as its unchanged child. No existing running job is adopted. Roll back through a reviewed source revert only when no invocation is active; keep private records for any outstanding/unknown owner. Do not remove custody files or release ownership merely because an observing client ended.

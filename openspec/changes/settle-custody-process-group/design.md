# Context

`executeOwnedCommand` spawns `pnpm test:docker` detached (its own process group) and, in the `close` handler, sets `settled = groupIsAbsent(child.pid)` once. `groupIsAbsent` (`scripts/trusted-docker-record.mjs`) returns true only on `ESRCH` and rethrows any other error, which the owner records as `failure = 'identity'`. `command.settled` then gates producer and browser settlement, cleanup assessment and `terminalStatus` (`settled === false` → `unknown`). The terminal result is published once and never revised.

Governing invariant (AGENTS.md, Trusted Docker verification): a group is absent only on a genuine `ESRCH` observed after the actual child-close/reaping boundary; EPERM and other observations are never absence evidence. The same section's fixture rule already polls group absence for up to 5000ms at 20ms (`platform/test/trusted-docker-fixture.ts` `waitForAbsence`).

# Decisions

1. **Bounded post-close observation.** After `close`, observe `kill(-pgid, 0)` repeatedly until a 2000ms monotonic window from `close` expires, at a 20ms interval: `ESRCH` → settled; group present (success) → observe again; `EPERM` → not absence, observe again; any other error → rethrow immediately (today's `identity` failure). At expiry a present group is unsettled with `failure: null`; if the last observation was `EPERM` the existing `identity` failure is kept. Never treat EPERM, zombies or "only zombies remain" as absence (a live `R` orphan was observed at close in 4/30 bare-pnpm traces). Rationale for continuing on EPERM: a fixture-review probe on this Darwin host (`sh -c 'sleep 0.2 & exit 0'`, 20 runs) always went present → `EPERM` (about 0.15–0.3ms) → `ESRCH` once the orphan's launchd reap completed; failing immediately would make Darwin settlement depend on poll phase. EPERM still never counts as absence, so this satisfies AGENTS.md's rule.
2. **Window derivation.** Observed residue cleared 2ms (container, docker-init) and about 50ms (bare pnpm under load) after close; Darwin's orphan-zombie EPERM interval was sub-millisecond idle, so with continued observation the 20ms interval only adds latency, not flakiness; the orphan only completes one `ps -A` listing. 2000ms gives about 40x margin over the slowest observed clearance, stays below the existing custody fixture's own 5000ms absence bound, and is negligible against a full Docker run. It is the only knob: if loaded runs breach the unchanged 10s status `waitFor`/20s test bounds, the result is reported, not absorbed by changing test bounds; no larger window is introduced without new measurement. Expiry fails closed (honest `unknown`), so the bound can only shorten an unsettled wait, never manufacture settlement. CI and VPS use systemd as PID1; their reaping latency is unmeasured, which is why the expiry outcome stays unsettled rather than inferred.
3. **Placement.** One canonical async helper beside `groupIsAbsent` in `trusted-docker-record.mjs` (or in the owner if no other caller needs it), used by the owner's close handler; `finished` resolves only after the observation settles. `groupIsAbsent` keeps its contract. No change to cancellation signalling, producer/browser settlement, cleanup assessment, terminal publication order or the status/cancel terminal reread.
4. **Regressions.** A new fixture mode makes the leaf, on SIGINT, spawn a short-lived same-group process with ignored stdio (so it does not hold the captured pipes) that sleeps a few hundred milliseconds, then exits without waiting for it. On current code the owner's single observation sees the live member and publishes `settled:false` (RED); with the fix the terminal is `settled:true`, `cleanup: confirmed`, and duplicate cancellation exits 0. The existing `persists the original command outcome when process-group observation is denied` case (always-EPERM preload) remains the denial negative: it now publishes after the 2000ms window, still `settled:false`, `failure: identity`, `cleanup: unconfirmed`, status `unknown`, cancel exit 1; its 10s status `waitFor` and 20s test bound are unchanged and must hold (startup plus 2s window). A second new mode's leaf, when it becomes ready (before writing `child-ready.json`), spawns a same-group member with ignored stdio (so it never holds the captured pipes and `close` still fires) that ignores SIGINT/SIGTERM and sleeps well past the window, and writes the member's pid/birth to a file under the owned temporary root. Teardown retires that single pid through the fixture's single-process settle (not the group form, whose pgid is pnpm's pid). Ordering: cancel once (exit 0, `cancellation-requested`), wait until `status` reports `unknown`, and only then send the late cancel, which must exit 1; a cancel sent while the owner is still inside the window legitimately returns `cancellation-requested`. Expected terminal: `settled:false`, `failure: null`, `cleanup.state: unconfirmed`, status `unknown`. Budget (20s test): setup and start wrapper (~1s idle), child-ready wait (existing 1s default, see #324), cancel wrapper, close plus 2s window, producer/browser/cleanup checks and publication, status polling (10s `waitFor`), late cancel, teardown member/group retirement (`waitForAbsence` up to 5s). The always-EPERM case's budget is: start returns at launch publication, child spawn and leaf run, close plus 2s window, checks and publication, inside its unchanged 10s `waitFor` (about 3–4s idle).
5. **Darwin dispatch warm-up (test-only).** In `trusted-docker-audit.integration.test.ts`'s selected-dispatch case, exec the freshly written fake `docker` once, untimed and outside the witness/journal protocol (a mode that exits before touching the witness), before the timed `spawnSync`/async dispatch. The 2000ms and 2000ms fixture bounds and every assertion are unchanged. Its evidence is the #321 measurement plus one loaded concurrent run; it is not deterministically reproducible.

6. **Distinguishing failure evidence.** The existing `cancels the actual pnpm child tree and preserves the terminal result on late cancellation` case (`trusted-docker-custody.integration.test.ts:338-345`, where CI failed) and the new custody regressions read the sanitized terminal (`command.{exitCode,signal,settled}`, `interruption`, `failure`, `cleanup.state`) and pass it as the assertion message before asserting duplicate-cancel status; the dispatch writer reports inner dispatch `status`, `signal`, `error.code` and elapsed milliseconds on stderr before exiting nonzero. No credentials, proxy values or raw environment are printed. Assertions are unchanged.
7. **Documentation.** AGENTS.md Trusted Docker verification (the Darwin zombie/EPERM paragraph) states the bounded post-close window, ESRCH-only settlement, EPERM continued observation and fail-closed expiry. Rule-file human review remains deferred.

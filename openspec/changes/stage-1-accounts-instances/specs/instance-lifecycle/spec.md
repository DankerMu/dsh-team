# instance-lifecycle

## Purpose

每个用户恰好拥有一个实例。平台在用户需要时启动它，空闲时停止它，并保证停止或重建后用户的文件、Session 和设置都还在。

## ADDED Requirements

### Requirement: 一个用户恰好一个实例

平台 MUST 为每个用户维护至多一个实例，实例由一个容器和两个持久卷（DSH 状态目录、工作目录）组成。

#### Scenario: 并发的两次启动只产生一个容器

- **WHEN** 同一用户的两个浏览器同时触发实例启动
- **THEN** 只有一个容器被创建，两个浏览器最终连到同一个实例

#### Scenario: 两个用户各有自己的卷

- **WHEN** 用户 A 和用户 B 的实例都启动过
- **THEN** 存在四个卷，A 的两个只挂在 A 的容器上，B 的两个只挂在 B 的容器上

### Requirement: 登录后按需启动

用户已登录而实例未运行时，平台 MUST 在用户访问工作台时启动实例，并在实例就绪前向用户显示等待状态。实例就绪 MUST 以“DSH 界面能以该用户的身份正常返回”为准。

#### Scenario: 首次登录

- **WHEN** 新注册的员工第一次打开工作台
- **THEN** 平台创建并启动其实例，员工先看到等待页，实例就绪后自动进入 DSH 界面，可以直接输入

#### Scenario: 实例已在运行

- **WHEN** 实例运行中的员工打开工作台
- **THEN** 直接进入 DSH 界面，不出现等待页

#### Scenario: 启动超时

- **WHEN** 实例在 60 秒内没有就绪
- **THEN** 平台停止该容器，把实例标记为出错，等待页显示启动失败并提供重试，同时提示仍失败时联系管理员；管理员在后台能看到最后的容器日志

#### Scenario: 平台会话有效而实例已停止

- **WHEN** 实例被空闲回收后，平台会话仍有效的员工不重新登录，直接打开工作台
- **THEN** 员工看到等待页，实例被启动，就绪后进入 DSH 界面
- **AND** 任务12.5验证沿用同一有效平台会话：HTML首页请求先重定向到等待页且不隐式启动，随后调用既有显式启动接口；就绪后新容器使用原来两个卷，先前完成的Session及完整历史消息和工作文件内容保持不变，不以重新登录或重建Session代替恢复

#### Scenario: 出错后重试

- **WHEN** 实例处于出错状态的员工在等待页点击重试
- **THEN** 平台重新启动该实例；就绪后进入 DSH 界面，再次失败则显示新的失败
- **AND** 就绪失败时保留的停止容器在显式重试且配置/容量准入后，由原用户生命周期队列按精确归属退役并用原两卷重建；准入拒绝或身份、账号、取消、退役/审计失败时不得继续创建新容器，不以测试夹具删除容器或修补数据行代替生产重试

### Requirement: 同时运行的实例有上限

处于启动中和运行中的实例总数达到配置的上限时，平台 MUST 拒绝新的启动，并 MUST NOT 为此停止任何已有实例。

#### Scenario: 上限已满

- **WHEN** 运行中的实例数等于上限，另一个实例未运行的员工打开工作台
- **THEN** 该员工看到“当前使用人数已满，请稍后再试”，没有新的容器被创建，已运行的实例不受影响

#### Scenario: 有人空出位置后可以进入

- **WHEN** 上限已满时一个实例停止，随后等待中的员工重试
- **THEN** 其实例正常启动

### Requirement: 网关活动记录

网关 MUST 按已认证用户维护活动连接数和最后活动时间；连接数为当前进程的实时状态，最后活动时间写入既有 `instances.last_activity_at`，每个用户成功写入的间隔 MUST 至少为60,000毫秒。活动记录 MUST NOT 改变实例生命周期状态或绕过既有每用户串行队列。

#### Scenario: 长连接打开和断开

- **WHEN** 已认证用户建立一个网关长连接，随后断开
- **THEN** 活动连接数从1变为0，最后活动时间更新为断开时刻，并在正常的限频写回中持久化
- **AND** 其他用户的计数和时间不变；HTTP响应结束后留存的keep-alive socket不算活动连接

#### Scenario: 同一分钟的活动合并

- **WHEN** 同一用户在一次成功写回后的60,000毫秒内发生多次连接活动
- **THEN** 内存保留最新活动时间，不增加持久化写入；达到下一次可写时机后写回最新观察值
- **AND** 生命周期工作阻塞期间不会积累多个待执行活动写入或在解除阻塞时突发写入

#### Scenario: 生命周期和退出期间的活动

- **WHEN** 同一用户的启动或对账仍在进行时需要写回活动，或平台正在退出
- **THEN** 写入遵循原有用户队列，不使完整行身份栅栏误判；数据库关闭前已提交的活动工作结清，关闭后没有定时器继续写入
- **AND** 退出时不绕过分钟限频，不为保存不足一分钟的尾部观察值延迟退出

### Requirement: 空闲后停止

实例在没有任何浏览器连接、且没有运行中的任务的状态下持续达到配置的空闲分钟数后，平台 MUST 停止它。只要有浏览器连接或运行中的任务，平台 MUST NOT 以空闲为由停止实例。

任务包 1.1 已确认采用 DSH `POST /api/session/list` 的 `result.value.items[].running`（协议和观测限制见 `design.md` 决定 9）。任一 Session 的值为 `true` 表示有任务；列表不完整、请求失败或响应无有效判据时属于未知，不得当作空闲。

#### Scenario: 无连接达到空闲时间

- **WHEN** 员工关闭全部浏览器页面，且没有任务在运行，这一状态持续达到空闲分钟数
- **THEN** 平台停止该实例

#### Scenario: 有打开的页面时不回收

- **WHEN** 员工保持一个 DSH 页面打开但不操作，时间超过空闲分钟数
- **THEN** 实例保持运行

#### Scenario: 有运行中的任务时不回收

- **WHEN** 员工提交一个长任务后关闭浏览器，任务运行时间超过空闲分钟数
- **THEN** 任务运行期间实例不被回收

#### Scenario: 空闲时间可调

- **WHEN** 管理员把空闲分钟数从 30 改为 5
- **THEN** 此后的空闲判定按 5 分钟执行

#### Scenario: 任务状态未知或刚结束

- **WHEN** 无浏览器连接，但任务列表请求失败、超时、截断或无完整有效判据，或者先前运行中的任务刚被观察为结束
- **THEN** 未知状态不触发停止；首次重新确认无连接且无任务时重新计算连续空闲时间，不把旧的用户活动时间当作任务结束时间

#### Scenario: 检查期间重新活动

- **WHEN** 空闲检查正在等待任务状态或原有用户队列，用户出现新连接、短请求、显式启动请求，或当前实例身份发生变化
- **THEN** 原空闲候选失效，不按陈旧观察停止活跃实例或替换后的实例
- **AND** 已经准入的空闲停止期间新请求不转发到正在退役的端点，停止仍保留原有精确归属、审计和卷保护

### Requirement: 停止和重建后数据恢复

实例停止后再启动，或容器被删除后重建，用户的文件、Session 和设置 MUST 保持不变。平台 MUST NOT 承诺被中断的任务继续执行。

#### Scenario: 停止后再启动

- **WHEN** 员工在工作目录生成一个文件并完成一轮对话，实例被停止后员工再次登录
- **THEN** 该文件内容不变，该 Session 出现在列表里且历史消息完整

#### Scenario: 删除容器后重建

- **WHEN** 上述实例的容器被删除，员工再次登录
- **THEN** 平台用同样的两个卷重建容器，文件和 Session 与删除前一致

### Requirement: 新实例可以直接使用

新实例 MUST 预置一个指向工作目录的工作区，界面为中文，且不出现上游的预览版公告。

任务包 1.2 已验证具体机制（`design.md` 决定 10、12）：工作区存储预置，加本仓库 `plugins/zh-locale/` 客户端插件及 canonical roster patch；非 loopback 首次进入和刷新均须满足上述要求。生产镜像及受管配置复用这些交付文件，不修改 DSH 源码或以浏览器预置状态代替实例配置。

#### Scenario: 首次进入

- **WHEN** 新员工的实例第一次就绪
- **THEN** 输入框可用，不需要先选择工作目录；界面文字为中文；没有公告弹窗

#### Scenario: 镜像首次填充不携带已有 Session

- **WHEN** 新员工通过平台登录、启动实例，并以全新浏览器首次进入网关
- **THEN** 镜像填充的工作区登记指向 `/data/work`，初始 Session 索引为空；DSH 浏览器不经工作区选择即可创建属于该员工的新 Session
- **AND** 实际 Session 的 cwd 为 `/data/work`，首次进入与刷新均为中文、无公告且输入框可用，浏览器不持有 DSH cookie

#### Scenario: 已有状态卷不被种子覆盖

- **WHEN** 已含员工工作区登记和 Session 数据的状态卷被新容器重新挂载
- **THEN** 镜像的首次填充种子不覆盖该卷里的工作区、Session 或工作文件
- **AND** 另一个员工的全新卷不包含前一个员工的 Session 标识或工作内容

### Requirement: 资源上限

每个实例 MUST 受配置的 CPU 和内存上限约束，上限在实例下次启动时生效。

#### Scenario: 默认上限

- **WHEN** 未改动配置时启动一个实例
- **THEN** 该容器的 CPU 上限为 2 核，内存上限为 4G

#### Scenario: 超出内存只影响自己

- **WHEN** 一个实例内的进程申请超过上限的内存
- **THEN** 该实例内的进程被终止或实例退出，其他实例和平台不受影响

#### Scenario: 修改设置只影响后续新建实例

- **WHEN** 管理员持久化新的CPU与内存上限后创建另一个用户容器
- **THEN** 新容器使用更新值，已有容器保留原上限，所有新建容器都有512进程上限
- **AND** 内存与内存加交换空间上限相同，不通过额外swap绕过内存限制

### Requirement: 每个实例有唯一且稳定的主机名

每个实例的容器 MUST 有一个由用户标识派生的主机名，不同用户不同，同一用户重建后不变。

#### Scenario: 重建后主机名不变

- **WHEN** 用户 A 的容器被删除并重建
- **THEN** 新容器的主机名与原来相同，且与用户 B 的不同

### Requirement: 管理员重启实例

管理员 MUST 能重启指定实例（运行中、已停止或出错的都可以），以及一次重启全部运行中的实例。

#### Scenario: 重启单个实例

- **WHEN** 管理员对运行中的实例执行重启
- **THEN** 该实例停止后重新启动并就绪，用户数据不变，该用户已打开的页面在重连后可继续使用

#### Scenario: 重启出错或已停止的实例

- **WHEN** 管理员对出错或已停止的实例执行重启
- **THEN** 该实例被启动；就绪后状态为运行中，再次失败则状态为出错并显示新的错误

#### Scenario: 批量重启只选择操作开始时运行中的实例

- **WHEN** 管理员请求重启全部运行中的实例
- **THEN** 平台 MUST 只处理该次操作开始时捕获的运行中实例，不启动原本已停止、出错或之后才开始运行的其他实例
- **AND** 平台 MUST 保留已完成的物理操作和审计，遇到失败不得声称整个批次已全部重启就绪

#### Scenario: 重启与禁用不交叉恢复实例

- **WHEN** 同一用户的管理员重启或禁用操作仍在处理
- **THEN** 相互冲突的管理员操作 MUST 被拒绝，而不是绕过已有实例生命周期所有者交叉执行
- **AND** 重启 MUST NOT 恢复禁用账号的运行权限，已有平台会话只在仍有效时允许页面重连

#### Scenario: 启动受理不等于完成就绪

- **WHEN** 重启接口返回实例仍在启动中的受理状态
- **THEN** 平台 MUST 通过既有状态查询报告其最终运行或新的启动错误，不把启动中报告为已完成就绪

### Requirement: 重置实例配置

管理员 MUST 能把指定实例的 DSH 配置恢复为镜像里的初始状态。重置 MUST NOT 改动用户的文件和 Session。

#### Scenario: 配置被写坏后恢复

- **WHEN** 某实例的 DSH 配置文件被写成无法解析的内容导致启动失败，管理员执行重置实例配置
- **THEN** 该实例能正常启动，工作目录里的文件和已有的 Session 都还在

### Requirement: 平台重启后实例状态一致

平台进程重启后 MUST 以容器的实际状态为准恢复对各实例的认识。

#### Scenario: 平台重启时有实例在运行

- **WHEN** 两个实例运行中时平台进程重启
- **THEN** 平台恢复后把这两个实例识别为运行中，对应的员工不需要重新启动实例即可继续使用

#### Scenario: 平台容器被重建

- **WHEN** 两个实例运行中时平台容器被删除并重新创建
- **THEN** 平台恢复后重新连上这两个实例，对应的员工不需要重新启动实例即可继续使用；连不上的实例被停止并标记为出错

#### Scenario: 重建后恢复保留实例身份与凭据

- **WHEN** 新平台进程的编排器对两个原有就绪实例恢复网络连接并重复对账
- **THEN** 实例容器、上游地址、有效DSH cookie和数据卷保持不变，平台可访问两个实例，健康实例不产生额外启动或停止审计

#### Scenario: 网络恢复失败后的出错状态可重试

- **WHEN** 验证过的运行实例无法接入平台，平台安全停止删除它并将索引标记为出错
- **THEN** 出错状态保留安全错误说明，运行身份与凭据清空，状态及error原因停止审计原子提交；重复停止和对账不丢弃错误，新启动可重新创建实例，数据卷保留

#### Scenario: 无对应容器的受管网络被回收

- **WHEN** 对账发现带正确用户标签和规范名称的实例bridge，且重新检查确认没有对应规范容器或索引容器
- **THEN** 仅在端点为空或只有验证过的平台端点时断开该平台端点并删除该网络，不修改数据卷或其他网络

#### Scenario: 网络清理遇到不可信状态

- **WHEN** 网络身份或当前索引改变、存在对应容器或不明端点，或Docker查询结果无法确认不存在
- **THEN** 平台不强制清理该网络或端点，错误明确；不得将未知查询结果当作孤儿资源

### Requirement: 平台经显式 Unix socket 访问 Docker

平台 Docker 客户端 MUST 通过配置的 Unix socket 使用 HTTP 请求，并区分 JSON、流式日志和带 HTTP 状态码的错误，不隐式切换到其他传输地址。

#### Scenario: Docker JSON 与错误响应

- **WHEN** 客户端读取 Docker 版本或查询一个不存在的容器
- **THEN** 前者得到实际版本 JSON，后者得到携带404状态码的错误
- **AND** 配置的 socket 不存在时，连接错误指出该 socket 路径

#### Scenario: Docker 日志增量消费

- **WHEN** 非TTY日志帧跨多次网络传输抵达或多帧合并抵达
- **THEN** 按顺序增量输出正确stdout/stderr载荷字节，不把帧头当作日志，不等待无限日志流结束
- **AND** 截断或非法帧失败，消费者取消时关闭响应资源

### Requirement: 按用户创建并复用持久卷

平台 MUST 为用户创建或复用 `dsh-team-home-<id>` 和 `dsh-team-work-<id>`，并确认两者的 `dsh-team.user` 标签匹配用户标识；不得通过删除重建实现复用。

#### Scenario: 重复创建及不同用户隔离

- **WHEN** 同一用户请求卷两次，另一用户也请求卷
- **THEN** 前者得到同一对卷，两个用户共四个不同的卷，所有卷的用户标签正确

#### Scenario: 同名卷归属冲突

- **WHEN** 同名卷的用户标签缺失或属于其他用户
- **THEN** 操作失败，不返回可使用的卷对，不删除、接管或重新标记该卷

#### Scenario: 第二个卷创建失败

- **WHEN** 第一个卷已就绪但第二个卷创建失败
- **THEN** 操作报告失败并保留第一个卷；后续重试复用它而不丢失持久数据

### Requirement: 安全创建并启动用户容器

平台 MUST 使用同一用户镜像的完整受管配置输入和该用户的两个持久卷，创建名称 `dsh-team-u-<id>`、主机名 `u-<id>`、用户标签匹配的非特权容器；覆盖层只读挂载，seccomp配置以文件内容交给Docker，DSH信任的平台authority取自平台配置。

#### Scenario: 创建并启动后索引真实回环端点

- **WHEN** 用户容器成功创建、启动且Docker检查返回其3080端口的回环绑定
- **THEN** 仅发布到127.0.0.1的随机端口被存入instances，容器标识和镜像信息一致，审计存在实例创建和实例启动事件
- **AND** 状态仍为starting，启动接口不宣称DSH已经就绪，不挂载Docker socket且不启用特权或未受限沙箱

#### Scenario: 重建保留稳定身份

- **WHEN** 该用户容器被移除后通过同一操作重新创建
- **THEN** 容器主机名保持不变，复用原有状态卷和工作卷

#### Scenario: 启动或索引失败不伪造成功

- **WHEN** Docker创建、启动、检查或对应数据库与审计事务失败
- **THEN** 操作返回失败，不返回未经验证的端点或伪造就绪状态，不删除用户持久卷，不在Docker动作成功前记录其成功审计

### Requirement: 平台托管当前实例的DSH认证cookie

平台 MUST 从当前用户实例的真实启动日志提取令牌，经node:http显式设置平台authority为Host换取DSH cookie，并仅将cookie保存在该当前实例的数据库记录中；令牌和cookie不得出现在平台日志、审计或公共返回值中。

#### Scenario: Host绑定的实例认证

- **WHEN** 平台为当前实例换取cookie并使用同一Host请求首页
- **THEN** DSH返回200，而同一cookie换另一个Host请求首页返回401

#### Scenario: 过期交换结果不能覆盖新实例

- **WHEN** 交换期间实例身份、端点、状态或账号可用性发生变化
- **THEN** 旧交换结果被拒绝，不覆盖新的cookie或实例记录；交换失败不保留本次已清除的旧cookie

### Requirement: 认证就绪与安全启动失败记录

实例只有在启动令牌换取cookie后、使用平台authority和该cookie请求首页得到200时，MUST 被标记为运行中并记录实例就绪审计。60秒内未就绪或已提前退出时，平台 MUST 停止该当前容器并将实例标记出错，保存去除凭据后的最后50行日志并写启动失败审计；不得删除容器或用户持久卷。

#### Scenario: 正常启动完成认证就绪

- **WHEN** 当前starting实例使用其新cookie和平台Host请求首页得到200
- **THEN** 该实例原子转为running并记录instance.ready，凭据仅在服务端

#### Scenario: 错误覆盖层导致启动失败

- **WHEN** 当前实例因错误覆盖层退出或60秒内未认证就绪
- **THEN** 该容器被停止，实例为error且最近错误包含实际脱敏启动日志，审计存在instance.start-failed；令牌和cookie均不出现在错误或审计中

#### Scenario: 旧就绪结果不影响替换实例

- **WHEN** 观察就绪期间当前实例身份或账号状态已改变
- **THEN** 旧结果不得将新实例标记运行中、覆盖其错误信息或停止其容器

### Requirement: 停止并移除容器时保留用户数据卷

平台 MUST 只停止并删除当前用户的受管容器，保留状态卷和工作卷，清除失效的容器端点与DSH cookie，并原子记录实例停止状态和调用方提供的停止原因审计。停用账号的实例仍 MUST 可以停止。

#### Scenario: 停止删除后重建恢复文件

- **WHEN** 状态目录与工作目录各有文件，实例被停止删除后重新创建
- **THEN** 新容器复用原来两卷且两个文件内容不变，原容器已不存在，实例停止审计原因等于调用方值

#### Scenario: 部分失败不伪造停止删除成功

- **WHEN** Docker停止或删除失败，或删除后数据库审计事务失败
- **THEN** 操作报告失败而不写虚假的成功审计，不删除卷；已删除但未提交的记录可在后续调用确认原ID不存在后完成一致的状态与审计

### Requirement: 同一用户生命周期操作串行

同一平台数据库生命周期内，同一用户的启动、凭据获取、就绪和停止操作 MUST 按提交顺序执行，不能相互重叠；不同用户 MUST 不因彼此的生命周期操作而等待。

#### Scenario: 十次并发启动只创建一次

- **WHEN** 同一用户同时发起十次启动
- **THEN** 只创建一个当前受管实例，后续启动验证并返回同一实例，创建和启动审计不重复

#### Scenario: 不同用户与失败队列隔离

- **WHEN** 用户A操作阻塞或失败，用户B启动，同时A还有后续操作
- **THEN** B独立推进，A后续操作在前项实际结束后按序执行，不因前项拒绝或排队取消而永久阻塞

### Requirement: 并发容量准入不超额

平台 MUST 将持久starting/running实例和尚未持久化的正在启动请求一并计入同时运行上限，不重复计数；不同用户竞争最后名额时只允许一个新实例启动。已验证的当前实例复用不消耗新名额。

#### Scenario: 最后名额被并发请求竞争

- **WHEN** 上限为1且两个用户同时启动
- **THEN** 只有一个获准创建，另一个返回full且不改实例/审计/覆盖层，不停止已存在实例

#### Scenario: 停止释放名额且未配置优先

- **WHEN** 已占名额实例完成停止删除，另一用户重新启动；或请求缺少模型配置且名额已满
- **THEN** 前者可以启动，后者返回unconfigured且不创建容器或写error状态

### Requirement: 对账修正失配且保留健康实例

平台启动对账 MUST 以验证过的容器身份与实际状态修正实例索引；不能把 Docker 错误当成容器不存在，不能因重建编排器而重启健康实例或丢弃其凭据。

#### Scenario: 索引中的运行容器实际不存在

- **WHEN** 索引是运行中且精确容器ID查询返回404
- **THEN** 对账将索引修正为已停止并清除运行地址和凭据，保留数据卷，不操作同名但不同身份的容器

#### Scenario: 容器仍运行但索引没有凭据

- **WHEN** 精确验证的用户容器仍运行但索引没有DSH cookie
- **THEN** 对账通过既有安全停止删除流程收回该容器并记为已停止，不重新获取凭据、不删除数据卷

#### Scenario: 已有健康实例跨编排器重建保持可访问

- **WHEN** 两个已就绪实例运行时重建编排器并等待对账完成
- **THEN** 两者仍为原实例，凭据和地址保留，认证请求仍成功且没有额外启动或停止审计

### Requirement: 认证实例启动与状态入口

平台 MUST 提供当前登录用户的 `POST /_platform/api/instance/start` 和 `GET /_platform/api/instance`，仅前者触发员工按需启动。成功响应 MUST 仅含 `status` 和 `reason`，不得暴露实例凭据、地址或内部诊断。生产进程 MUST 在接收流量前完成既有实例对账，在关闭数据库前结清所有拥有的启动和就绪工作。

#### Scenario: 单一入口和幂等启动

- **WHEN** 有效员工调用启动接口，并在启动中或运行中重复调用
- **THEN** 同一用户复用同一启动到就绪工作及容器，接口返回当前机器状态；就绪后其网关首页可正常返回DSH
- **AND** 状态GET与首页/长连接查询本身不会创建或启动容器

#### Scenario: 身份与安全投影

- **WHEN** 员工在请求中伪造其他用户或实例标识，或无有效平台会话调用实例入口
- **THEN** 标识不能改变当前用户归属，无有效会话得到401；任何实例状态响应都不包含DSH cookie、模型密钥、内部地址或last_error

#### Scenario: 启动与退出顺序

- **WHEN** 对账尚未完成，或者已有启动/就绪工作尚未完成时平台开始退出
- **THEN** 前者不接收实例流量，后者拒绝新启动并等待实际工作及清理结束后才关闭数据库

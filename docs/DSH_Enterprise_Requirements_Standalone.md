# 企业内网 DSH 多用户办公平台：项目需求与架构分析任务

## 任务说明

你负责本项目的产品分析、系统架构与工程规划。项目目标、环境、功能范围、设计约束和交付标准均在本文中给出。请依据本文及能够实际访问的本地代码和配置开展工作。

本文中的“必须”“需要”“不提供”“首期不做”定义交付范围；“建议”“优先评估”表示设计方向；“待确认”“需核实”表示尚缺少事实依据或需要项目方决定的细节。不得混淆这三类信息。

当前任务是完成源码审查、需求映射、架构选型、分阶段开发计划和验收方案。可以输出分析文档并进行不影响现有服务的验证；暂不进行大规模代码修改、仓库合并、生产部署或现有服务升级。工程实施应在架构方案获得项目方确认后进行。

术语约定：

- DSH：DeepSeek Harness，作为个人 Agent 运行环境与工具执行底座。
- 用户实例：分配给某一员工、与其他员工隔离的 DSH 运行环境，不等同于 Session 或专业 Agent。
- Session：员工工作台中的一段任务会话；一个员工可以拥有多个 Session。
- 办公 Agent：具有专门职责、指令、Skills 和工具配置的任务角色，原则上在所属员工的 DSH 实例内运行。
- 个人工作文件：员工在 DSH 工作空间上传或生成的文件，可以按本项目要求预览和编辑。
- 团队知识资料：由现有 RAGFlow 维护的共享资料；DSH 只读获取目录并执行检索，不修改原件。

## 二、固定产品要求

以下要求构成本项目的功能与部署基线；已有外部服务与需要开发的功能按各章节分别标明：

- 几十名内部员工使用同一个 Web 入口，采用邮箱账号，由管理后台统一管理。
- 每人独立 DSH 实例、工作空间、Session、私有文件及必要的运行状态。
- 自由对话是主要入口，但必须内置一批实际可用的行政办公 Agent。
- 模型按需调用已批准、已启用的能力；熟练用户可以手动指定 Agent、Skill 或工具。
- 内部插件由管理员审核发布；核心插件统一配置，其他批准插件由员工按需启用。
- 所有模型都在内网，管理员统一配置，员工不自行填写服务密钥。
- 全部部署和运行环境完全隔离，没有公网访问渠道。
- 复用现有 RAGFlow 作为共享知识底座，不再自建团队知识库系统。
- 所有员工看到统一接口可列出的全部团队知识库，不做部门、人员级知识权限划分。
- RAGFlow 插件页面只读展示知识库名称和库内文件列表；用户可以选择当前会话使用哪些知识库。
- 不在 DSH 中新建、修改、上传、删除或触发解析任何 RAGFlow 知识资料。
- 个人工作文件支持 HTML 等预览，Word、Excel 编辑优先复用现有 ONLYOFFICE 插件。
- 接受人工与 Agent 同时修改同一文件时后写覆盖；不建设人机编辑锁、冲突合并或强制交接流程。

“知识库全员共享”不代表“个人工作空间共享”；“接受同一文件并发覆盖”不代表可以放弃不同用户之间的文件隔离。

## 三、员工界面与日常工作流程

员工登录后进入自己的工作台，通过自然语言提出任务、上传文件、查看执行过程、获取结果、下载产物，并继续历史 Session。不要求先点击某个助手卡片才能开始工作。

建议界面由会话／工作空间导航、自由对话区和可展开的文件预览／编辑区组成。尽量复用现有界面，不为了布局重写全部前端。界面以中文和业务名称为主，不让员工处理 profile、端口、容器、包名或 API Key。

输入区可以提供可选的 Agent、Skill／工具和知识库选择控件。普通用户直接对话，熟练用户可以显式指定能力。采用菜单、搜索、@ 或 / 等方式由实际 DSH 扩展能力决定，不假定某种语法已经存在。

一个用户可以有多个 Session，Session 属于该用户，并关联明确的工作文件范围。关闭网页不等于删除任务或数据；后台任务是否继续运行、重新连接如何恢复展示，需要核实并说明。

执行中、等待确认、执行失败、已完成，以及文件正在保存、保存失败等状态应清楚展示，不能将工具失败包装成成功回答。生成文件必须真实落盘且可以获取，不只输出一个看似下载链接的字符串。

## 四、内置行政办公 Agent：必须交付

### 4.1 产品参考与实现方式

办公 Agent 的产品参考名称为 Workbody，准确拼写及对应产品待核验；WorkBuddy 可作为名称核对对象，不直接将两个名称视为同一产品。参考重点是行政办公任务覆盖、专家角色划分，以及 Agent、Skills 和工具的组织方式。

产品参考用于辅助设计，不是平台运行依赖。不得假设参考产品开源、已经取得其完整 Agent 配置，或可以复制非公开提示词。使用可获得的公开资料时记录来源；资料不可得时，根据第 4.3 节的候选集合开展设计，明确候选由本项目提出，不因外部参考缺失而停止仓库分析。

必须交付一批具备明确职责和行为配置的办公 Agent，而不是只做名称不同的卡片，也不能把这项要求降级为以后再做。优先映射到 DSH 实际支持的 Agent、预设或子 Agent 机制，不要求每个角色都单独启动容器。

Agent 负责特定任务与执行组织；Skill 表达方法、规范和模板；工具／插件承担知识检索、文件读取、文档生成等实际动作。

每个内置 Agent 应具备稳定标识、中文名称、职责、适用任务、指令、关联 Skills、允许调用的工具、统一模型策略引用、输入输出约定、版本及启用状态，并至少有一个可执行的验收任务。

### 4.2 使用方式

默认提供综合办公 Agent，根据任务选择或调用专业 Agent、Skills 和工具。员工也可以手动指定专业 Agent。自动调用和手动指定都必须真实有效，而不是仅改变界面标签。

不要让每轮对话都机械地启动多个 Agent，也不要求首期建设可视化多 Agent 工作流编辑器。由源码能力与任务性质决定采用角色切换、专业配置还是子任务委派。

所有专业 Agent 和子 Agent 都在当前用户的隔离范围内工作，继承本次任务的文件范围、启用能力和知识库选择，不能换一个 Agent 就扩大为全库检索或读取其他用户资料。

### 4.3 首批候选

以下候选由本项目定义，不宣称对应某个外部产品的实际清单。请根据实际资料、工具和内网模型能力提出最终拆分与优先级：

1. 综合办公：理解任务、选择能力、组织最终结果。
2. 公文与材料写作：通知、请示、说明等材料起草，应用单位模板。
3. 材料校对：检查用词、结构、格式和材料内部的数据一致性，不伪装成完成了外部事实核验。
4. 会议纪要：基于文字记录提炼议题、结论、责任人与待办，不默认包含语音转写。
5. 工作总结与报告：整合工作材料，形成总结、情况报告和汇报材料。
6. 制度与知识检索：检索选定的 RAGFlow 知识库，提供有来源的解释。
7. 表格与数据分析：整理、合并、核对表格，进行统计、计算与图表输出。
8. 演示文稿：将材料整理成汇报结构及可交付的 PPTX，具体格式能力通过测试确认。
9. 会务与活动方案：生成议程、分工、执行清单和方案，不默认操作外部业务系统。
10. 文件整理：在用户指定范围内分类、重命名、汇总文件，破坏性动作需要确认。

数量不必为了凑数固定为十个，但应交付一批有实际区别的办公 Agent。依赖公网数据的场景不直接照搬；每个 Agent 都应验证真实工具调用和产物，而不只是写角色提示词。

## 五、每用户独立实例与持久化

必须实现：

用户 A → DSH 实例 A → A 的工作空间、Session、私有文件
用户 B → DSH 实例 B → B 的工作空间、Session、私有文件

不接受所有人共用一个 DSH runtime、仅过滤会话列表的替代方案。独立目录、端口或 profile 本身也不能直接等同于操作系统级隔离。

优先采用每用户独立容器或等效隔离，说明进程、文件系统、网络、资源和凭据边界。运行配置、状态路径、环境变量和启动参数必须从源码确认，不凭空预设 DSH_HOME 或其他配置项。

可以共享只读镜像、批准插件制品、内网模型、RAGFlow 和文档服务，但用户的可写状态、会话、上传和生成文件、必要插件状态必须隔离并持久化。

平台负责实例创建、启动、就绪、异常、停止和恢复，以及登录身份到实例的可信路由。优先评估按需启动和空闲停止；不能在任务执行、Office 编辑或保存期间无故回收实例。一个用户多个 Session 原则上共用其独立实例。

实例停止或重建后应能恢复文件、Session 和必要配置。不能把保留历史数据与运行中任务断点续跑混为一谈，后者须核实能力后说明。

HTTP、WebSocket／SSE、文件上传下载、预览和插件回调都必须校验归属。不能信任客户端提交的 user_id、runtime_url、session_id 或任意文件路径，也不能让员工绕过平台访问其他 DSH 上游。

用户实例不暴露宿主 Docker socket、平台管理密钥、其他用户存储及无关内网管理接口。配置合理的资源限制；说明单实例故障与共享宿主资源耗尽的不同影响，不承诺共享硬件绝对互不影响。

## 六、账号与管理后台

账号通过邮箱创建，由后台统一管理，至少区分管理员和普通员工。不需要公众注册、复杂组织树或企业 SSO。

建议采用邮箱作为登录名、密码登录、管理员创建／重置账号的简单流程，不默认要求邮件验证码或依赖公网邮件服务。具体初始密码与重置方式属于待确认的实现细节。

管理后台覆盖账号、实例状态、统一模型、内置 Agent、核心／可选插件、RAGFlow 连接及必要的日志。管理后台不包含 RAGFlow 知识内容的增删改页面。

账号禁用需要处理已有登录态、长连接和实例访问，不能只阻止下一次登录。排障和审计保留必要操作记录，不默认记录全部对话与敏感文档，不记录明文密码或密钥。

管理员管理实例不自动等于产品中可以任意浏览员工私有内容。私有内容访问不是首期默认管理功能；也不要宣称宿主系统管理员在技术上绝不可能接触落盘数据。

## 七、统一内网模型配置

所有模型服务都在内网。管理员统一配置服务地址、凭据、可用模型、默认模型以及 Agent 的模型策略。员工无需自行填写服务密钥，不能通过修改个人实例覆盖受管策略。

底层使用 DeepSeek Harness，不代表只能使用某一家模型。需核实当前 DSH 与实际内网服务的协议、流式响应、工具调用和任务能力，不能仅验证普通聊天就宣布所有 Agent 可用。

优先复用现有内网模型网关；没有时评估最小可信代理或安全配置方式，不另建庞大的模型管理平台。不向浏览器或用户能任意读取的配置下发平台管理级长期密钥；实例调用凭据应在可行范围内受限、可撤销。

说明配置发布、更新、停用及回滚如何作用于用户实例和正在执行的任务。内网模型不可用时明确报错，不回退到公网模型。是否允许员工在批准模型中手动选择，作为可配置的交互建议。

DSH 不接管 RAGFlow 自身的检索、嵌入、重排等模型配置。

## 八、内部精选插件市场

这是内网批准能力目录，不是开放互联网插件商店。

管理员引入、审核、发布并固定版本，维护名称、中文说明、分类、来源、依赖和所需权限。插件、Skills、Agent 配置可以统一展示，但后台必须区分实际类型及安装／启用机制。

核心插件由管理员预配置并默认启用，例如 RAGFlow、必要文件处理和文档预览／编辑；核心能力的停用由管理员控制。其他批准插件由员工为自己的实例按需启用或关闭，不影响其他用户。

启用状态必须与实际运行一致。需要安装、重启或发现版本不兼容时明确提示，不能只切换页面上的开关。升级失败、回滚和各实例的版本状态应可核对，不要求首期实现所有插件无感热更新。

制品使用随部署交付的离线包或内网制品库。员工不使用 CLI，也不能通过平台安装任意 GitHub／npm 来源的插件。批准插件目录不是任意代码执行的完整安全边界，仍需用户实例隔离。

不要为了内部几十人使用而建设公共市场的交易、评分、开发者入驻或自动抓取功能。

## 九、RAGFlow 插件：只读浏览目录与选择检索范围

### 9.1 现有基础与范围

RAGFlow 已部署在内网，定位为公司所有智能体应用共用的知识底座。环境版本信息为 1.0.0／RC 系列，精确发行标签尚未核实。接入前从实际镜像 Tag、构建信息和接口行为确认版本；不能假定是正式版或某个特定 RC，也不能自行升级现有服务。

本项目只接入现有服务，不新建知识库后端、资料入库、解析、向量数据库或全量知识副本，不为每个 DSH 用户部署 RAGFlow。

所有登录员工共享同一个知识接口，看到该接入凭据实际可列出的全部团队知识库，不建立部门／人员级知识权限、个人 RAGFlow 账号或知识角色映射。这不意味着绕过 RAGFlow 自身认证访问其他资料。

### 9.2 插件页面必须提供只读浏览

RAGFlow 插件不能只有一个后台检索工具，还要有可以打开的知识库页面。员工在这里看懂“有哪些知识库，每个库里有哪些文件”。

主要展示知识库自身的名称／标题，不用 ID 作为主要标签，更不能把库内某份文件的标题当作知识库标题。简介和文件数量在接口实际提供时显示，缺失时不编造。ID 只用于后台绑定和请求。

员工可以展开或进入某个知识库，查看其中的文件名称列表。可以提供知识库名称搜索、文件名筛选、分页、刷新等只读交互。打开页面不必一次性加载所有文件，优先按需加载；分页不能遗漏却声称已经展示全部。

解析状态等附加信息仅在接口实际提供且有助于使用时展示。应区分加载中、空知识库、没有匹配文件和请求失败，不能把接口失败显示为“没有文件”。

这里所说的“知识库预览”仅指知识库名称及库内文件列表，不要求预览正文、下载原件、编辑文件或逐文件勾选检索范围。

明确不提供：新建知识库、修改名称或简介、上传文件、删除文件、删除知识库、触发解析、修改知识处理配置，以及任何 RAGFlow 内容写操作。知识维护继续在现有 RAGFlow 系统完成。

RAGFlow 地址、凭据等连接配置由平台管理员统一管理，属于接入设置，不是知识内容管理，普通员工不修改。

### 9.3 按 Session 选择检索范围

提供多选、全选和取消选择。勾选知识库表示当前 Session 使用它；展开查看文件只是浏览，两者必须分开，不自动联动。

插件页面提供选择时应明确当前作用的 Session；没有选定 Session 时仍可只读浏览，不能暗中修改某个全局默认。对话区显示当前选中的知识库名称，并可以提供快捷修改入口。

后台保存稳定 ID，前台展示最新名称；刷新或重开 Session 后恢复选择。一个用户的选择不改变其他用户，一个 Session 的选择不改变其他 Session。

每次提交任务时确定本次使用的知识范围。之后的选择修改对后续任务生效，不能让运行中任务随机换库。主 Agent、专业 Agent 和子 Agent 均继承该范围，只能在所选范围内检索，不静默扩大到未选知识库。

取消全部选择表示不查询团队知识库。不能因空列表、无效 ID、接口失败或知识库被删除而退回全库查询。已选知识库不可用时给出提示。

新 Session 的初始知识库选择是待决项：可以默认全选，也可以默认不选并提示员工选择。请提出建议并说明使用影响，不将某一种策略认定为固定要求。无论默认如何，员工主动取消全部选择后都表示不执行团队知识检索。

选择变化仅限制后续检索，不自动删除已经进入历史对话的资料片段。这是任务检索设置，不是知识访问权限或历史信息隔离机制。

### 9.4 检索、接口与凭据

接入并核实三类只读能力：知识库列表、指定知识库的文件列表、在选定知识库范围内检索。实际路径、字段、分页、认证和多库检索约束以当前部署文档与联调为准，不照搬未经核实的 API。

检索返回内容片段及真实来源，由 DSH 继续回答、写作或生成文件，不默认把整个会话转交 RAGFlow 的聊天助手。来源名称、片段位置、页码等仅使用真实数据，不编造。

只读目录不提供原件下载；检索结果可以显示实际用到的片段与来源标识。这两种呈现方式要区分，不把引用自动扩展成一个知识原件管理器。

统一密钥保存在可信后端，不暴露给浏览器或用户 Shell。可复用平台后端提供仅允许列表、文件列表和检索的受限代理，不做任意转发 RAGFlow 管理接口的通用代理，也不另造复杂知识权限平台。

无结果、超时、配置错误和服务中断应明确区分。RAGFlow 不可用不能阻止整个工作台启动，不能将失败回答成“已确认没有相关制度”。资料内容作为参考，不是改写平台权限的指令。

DSH 私有工作文件不自动上传 RAGFlow；RAGFlow 原件不接入下面的 Office 编辑回写流程。

## 十、个人文件预览与 ONLYOFFICE 编辑

### 10.1 目标与复用原则

用户工作空间中的文件应支持浏览、上传、下载及适用的预览。重点是 HTML 预览、Word／Excel 预览和网页编辑，以及人工保存后 Agent 能基于新内容继续处理。

先核实本地 DSH 已有的预览能力。Office 编辑的优先复用对象是 chendefine/dsh-sidebar-onlyoffice：

https://github.com/chendefine/dsh-sidebar-onlyoffice

该插件的具体依赖、是否需要 dsh-better-sidebar、兼容版本、许可证与保存机制均需检查其实际代码和文档；不能假定已安装、可直接兼容当前 DSH，或已经具备可运行的内网文档服务。不从零编写 Office 编辑器。

如果插件没有本地副本且研发环境无法联网，列出需要导入的源码或制品，先完成集成边界分析，不编造安装命令、依赖地址或测试结果。

以 DOCX、XLSX 为主要编辑格式；PPTX 等在实际支持并通过测试后纳入。旧 DOC／XLS 的转换、复杂排版、公式等支持范围需说明，不能笼统宣称完整兼容所有 Office 文件。

HTML 预览独立验证，不因接入 Office 插件就视为已经实现。使用受限渲染，避免生成的页面获得平台凭据或任意调用内网管理接口。

### 10.2 文档服务与正确回写

核实内网是否已有 ONLYOFFICE Document Server；没有时将其作为部署依赖评估，不假定装一个插件就具备编辑服务。核查离线部署、字体、授权及容量条件，不未经验证承诺某个版本可满足几十人并发编辑。

文档服务可以共享，但文档标识、获取地址、保存回调和落盘目标必须绑定正确用户、实例和文件。同名文件不能跨用户串读或覆盖。回调需要校验，路径和网络路由不能绕过私有文件隔离。

正常流程必须验证：Agent 生成文件 → 员工在线修改并保存 → 保存完成后 Agent 重新读取最新文件 → 继续处理并生成结果。不能让 Agent 一直使用旧缓存，也不能把编辑器本地状态当作文件已经写回成功。

### 10.3 文件并发编辑策略

首期不新增人机编辑锁、实时冲突合并、强制只读切换、保存交接按钮或专门的文件版本历史系统。保留插件已有的正常保存、刷新和提示机制。

人工与 Agent 同时写同一文件时，采用最后实际写入的内容覆盖原文件的策略。这可能丢失内容，界面简单提示：“请勿在 AI 修改此文件时同时编辑；人工修改保存完成后，再让 AI 继续处理。”

不能以“必须先解决多人协同编辑”为由阻塞首期，也不能把这一取舍宣传成无冲突编辑。顺序编辑时仍应正确保存、正确读取；跨用户隔离必须保留。

如果现有插件不兼容，说明具体问题并优先提出最小适配。只有存在无法复用的证据时才评估替代方案，并比较改动范围、离线部署和维护成本。

## 十一、完全内网交付与运维

运行环境没有任何公网访问渠道。模型、插件制品、RAGFlow、Office、字体和前端资源都必须在内网可用，不依赖公共 CDN、在线字体、公网模型、外部登录、遥测或运行时自动下载。

首次安装、实例创建和重建、插件启用、文档转换及更新的依赖都需要预置。使用内网制品仓或离线交付包，说明准备、导入、安装、升级和回滚步骤，不能只给在线 npm／curl 命令就宣称支持离线。

如需公网调研或准备依赖，只能在明确允许的外部准备环境进行，再按既定方式导入；不得要求生产内网临时放开公网。没有参考资料时如实注明，不编造调查结果。

优先匹配单机或少量服务器的容器化部署，不默认引入 Kubernetes、Kafka、多集群或复杂微服务。必要的健康检查、资源限制、日志、受控升级及备份恢复要保留。

部署级备份恢复属于基础运维，不要求实现面向员工的文档版本协作功能。容量测量区分账号人数、在线人数、活跃实例、并发模型任务和同时编辑文档数，不依据“几十人”直接保证性能。

## 十三、明确不做的事情

首期不做：第二套知识库后端或 RAGFlow 内容管理后台；知识库增删改、上传和解析操作；知识原件正文浏览、下载或编辑；部门／人员级知识权限系统；复杂 SSO 和组织树；公网插件市场；自研 Office 编辑器；人机编辑锁和冲突合并；强制先选助手的流程；复杂工作流设计器、计费、多集群等未提出功能。

设计文档、开发计划、界面和验收范围均应遵循这些限制。RAGFlow 连接设置、只读列表刷新和 Session 检索范围选择属于接入交互，不属于知识内容管理。

## 十四、分阶段实施建议

## 十五、验收要求

1. 两个邮箱账号登录同一网站，实际使用不同 DSH 实例和私有存储；文件与 Session 不串用。
2. 通过直接 API、长连接、路径、插件、Shell 或网络访问其他用户数据及平台管理资源的尝试被阻止。
3. 员工不配置模型密钥即可完成真实工具调用；无公网环境下仍可完成任务。
4. 自然语言任务能调用适当的内置办公 Agent、Skill 和工具；用户手动指定也有效，每个 Agent 有可验证的实际产物。
5. 核心插件由管理员配置；员工启停批准的可选插件只影响自己的实例，界面状态与运行状态一致。
6. 所有员工在 RAGFlow 插件页看到真实知识库名称，并能展开查看库内文件名称；不需要理解 ID，列表分页与错误状态正确。
7. 页面和后端不开放 RAGFlow 内容写操作，不提供知识原件编辑回写；个人工作文件不会自动进入团队知识库。
8. Session 仅选库 A、B 时，主 Agent 和子 Agent 不静默查库 C；选择可恢复，不影响别的 Session，空选择不误查全库。
9. 检索有真实来源；失败不伪装成查证成功；RAGFlow 中断不阻断其他工作台功能。
10. 用户工作文件可按约定预览／编辑；正常顺序下，人工保存后的内容能被 Agent 重新读取，并发写入按最后实际写入覆盖的策略处理，并展示提示。
11. 两个用户的同名 DOCX／XLSX 在编辑器、获取地址和保存回调中完全区分，不跨用户写回。
12. 实例停止或重建后恢复文件与 Session；Office 正常活动不被无故中断；异常与共享资源风险有验证说明。
13. 账号禁用和配置停用按策略失效，故障可排查，凭据不暴露于浏览器、日志或用户可任意读取的管理配置。
14. 离线安装、实例重建、插件启用、字体资源和备份恢复经过验证；并发容量有测量依据，不以网页能打开代替验收。

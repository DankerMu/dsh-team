# DSH 企业多用户办公平台：开发方案

日期：2026-10-03。本文是 `stage-change-pipeline` 的阶段输入：每个阶段给出目标、任务包、必读文档和完成条件。

- 需求依据：`docs/REQUIREMENTS_BASELINE.md`（下称“基线”，功能编号 F1–F48，决定编号 D1–D15）。
- 事实依据：`docs/DSH_Enterprise_Architecture_Analysis.md`（下称“分析”）。架构图和实测结果在那里，本文不重复。
- 验证脚本：`verify/phase0/`，一次性验证用，不是平台代码的起点。

## 1. 目标与成功标准

交付一个单机 Docker 部署的平台，满足基线全部功能需求，并通过基线第 7 节的 14 条验收。DSH 源码不改；所有定制通过平台代码、DSH 插件、受管覆盖层和镜像构建完成。

## 2. 约束与假设

| 类别 | 内容 |
|---|---|
| 约束 | DSH 源码不改（D1）；Node/TypeScript + SQLite（D2）；单机 Docker（D3）；完全离线运行 |
| 约束 | 版本钉定见基线第 4 节 |
| 假设 | 目标服务器上 bubblewrap 或 Landlock 至少一种可用。本机实测需要放宽 seccomp 和 `/proc` 屏蔽两项容器设置（分析 3.6）。阶段 1 第一个任务包验证，不成立则方案要改 |
| 假设 | `qwen3.6` 能稳定做工具调用。开发期用 `deepseek-v4.1-flash`，生产联调时重验 |
| 假设 | 内网各 RAGFlow 知识库用同一个嵌入模型。不成立则检索改为逐库请求后合并 |

## 3. 仓库结构

```
platform/                平台服务（一个 Node 进程）
  src/auth/              注册、登录、会话、密码          ← 参考 dsh-team-hub 的 passwords/users/auth
  src/admin/             管理后台 API
  src/orchestrator/      容器生命周期（Docker Engine API）
  src/gateway/           HTTP + WebSocket 反向代理、DSH cookie 托管
  src/managed-config/    生成每用户的受管覆盖层
  src/ragflow-proxy/     只读代理
  src/audit/             审计日志                        ← 参考 dsh-team-hub 的 audit
  src/db/                SQLite 表结构和迁移
  web/                   登录页、注册页、管理后台前端
plugins/
  ragflow/               DSH 插件：检索工具、知识库页面、输入区选择器
  office-agents/         DSH bundle：十个 preset + Skills
images/
  dsh-user/              用户镜像：DSH、pnpm、Python、bubblewrap、预装插件、better-sidebar 补丁
  seccomp/               容器 seccomp 配置
deploy/                  compose 文件、离线打包和导入脚本、备份恢复脚本
assets/fonts/            字体
docs/  verify/  resource/（只读参考，不入库）
```

## 4. 关键技术决定

阶段 0 的实测已经确定或逼出了下面这些做法。

| 编号 | 决定 | 依据 |
|---|---|---|
| T1 | 网关对上游始终使用一个固定的 authority（平台对外的 host:port），DSH 用 `--trusted-host` 放行它。不使用 `--public-url`（发行版没有） | 分析 3.2；DSH cookie 绑定请求的 Host |
| T2 | 网关读取容器 stdout 里的启动令牌，在服务端换成 DSH cookie 并保存，之后每个请求注入；浏览器只持有平台自己的登录 cookie。令牌交换用 `http.request`，不能用 `fetch` | 分析 3.2，已实测 |
| T3 | 受管覆盖层按用户生成，只读挂载，用 `--patch` 加载。内容：监听 `0.0.0.0`、模型配置、默认模型、去掉每个 preset 的联网搜索和抓取工具、Office 插件配置（含该用户容器的内部地址）、关闭 HTML 沙箱开关、权限预设。模型等部分所有用户相同，只有 Office 的内部地址按用户不同 | 分析 3.3、3.5，已实测；Office 插件的 `internalBaseUrl` 每个用户不同 |
| T4 | 容器启动命令：`dsh --profile web --patch <覆盖层> --no-open --trusted-host <authority>`；环境变量注入模型密钥和 `DSH_TELEMETRY_DISABLED` | 分析 2.3，已实测 |
| T5 | 插件和 profile 目录在镜像里预置；新用户卷首次挂载时自动带上。镜像升级时老用户卷的 profile 目录由平台在启动前同步 | 分析 3.6，前半已实测，同步逻辑待做 |
| T6 | `better-sidebar` 0.24.1 的补丁由用户镜像的构建步骤维护，版本不符时构建失败。同时向上游提需求 | 分析 3.5，已实测 |
| T7 | 每个容器 `--hostname` 取用户 ID 派生的唯一值 | 分析 3.5 |
| T8 | 容器安全设置：自定义 seccomp 配置放行用户命名空间相关调用，并解除 `/proc` 屏蔽。本机验证用的是整体关闭 seccomp，正式配置在目标机收敛 | 分析 3.6 |
| T9 | 网络：每个用户容器一个独立网络，网关和 Document Server 接入各网络。具体做法在阶段 1 验证 | 基线 F11 |
| T10 | RAGFlow 知识库选择存为 Session 事件（标记为可忽略），提交任务时快照；检索工具沿 Session 的 `parentSession` 回溯到根 Session 取选择 | 分析 3.4；`parentSession` 字段已实测，插件代码待写 |
| T11 | 插件前端与后端通信用插件自己注册的普通 HTTP 路由，不用 DSH 的类型化远程调用生成器 | 分析 2.3 |
| T12 | 平台不实现模型代理；不为每个用户申请独立密钥 | 基线 D7 |

## 5. 阶段划分

每个阶段结束时必须有真实可运行的链路。任务包的顺序就是依赖顺序。

### 阶段 1：账号、独立实例、对话、持久化

**目标**：两个邮箱账号注册登录后各自进入自己的 DSH 实例，完成带工具调用的真实任务；文件和 Session 互不可见；实例停止和重建后数据恢复；管理员能禁用账号。

**必读文档**：基线第 2、4、5.1–5.3、5.7 节；分析 2.3、3.2、3.3、3.6、6.1；`verify/phase0/README.md`。

| 任务包 | 内容 | 覆盖 | 验证 |
|---|---|---|---|
| 1.0 目标机探测 | 在 Ubuntu 22.04 amd64 上构建用户镜像，验证 `bash` 工具可用所需的最小容器安全设置，产出 seccomp 配置 | T8 | DSH 的 `bash` 工具在“工作区内修改”模式下：工作区可写、状态目录不可写 |
| 1.1 探针：DSH Web 接口 | 查明 0.2.0-rc.2 的 HTTP 接口实际路径和“是否有运行中任务”的判断方式 | F13 | 能从平台侧判断一个实例是否空闲 |
| 1.2 探针：预置工作区、中文界面、关闭公告 | 查明如何在新实例里预置工作区、设默认语言、去掉首次公告 | F15、F44 | 新实例登录后可直接输入 |
| 1.3 仓库骨架 | `platform/` 工程、SQLite 表结构和迁移、测试框架、lint | D2 | 空服务能起，测试能跑 |
| 1.4 账号 | 注册、登录、登出、改密码、会话 cookie | F1、F2 | 单元测试覆盖密码校验、会话过期、重复邮箱 |
| 1.5 用户镜像 | DSH、pnpm、Python、bubblewrap、预置 profile | T4、T5 | 镜像能启动 DSH Web |
| 1.6 受管覆盖层生成 | 按用户生成覆盖层文件 | T3、F17、F18、F24 | 用户改自己的配置后合成结果仍是受管值；合成配置里没有联网搜索和抓取工具 |
| 1.7 编排器 | 创建、启动、停止、删除容器；卷；唯一主机名；资源上限；读取启动令牌；就绪探测 | F8、F10、F12、F16 | 集成测试：起停两个实例，卷数据保留 |
| 1.8 网关 | 登录会话到实例的路由；DSH cookie 托管；HTTP、WebSocket、上传下载 | T1、T2、F9 | A 的会话访问不到 B；未登录 401；WebSocket 可用 |
| 1.9 按需启动与空闲停止 | 登录触发启动；等待页；空闲判定和回收 | F13、F14 | 有任务时不回收；回收后再登录数据还在 |
| 1.10 网络隔离 | 每用户独立网络 | T9、F11 | B 容器连不到 A 容器的任何端口 |
| 1.11 管理后台（账号和实例） | 账号列表、禁用启用、重置密码、实例状态、重启、重置实例配置 | F3、F4、F7 | 禁用后该用户的长连接在数秒内断开、实例停止 |
| 1.12 模型配置后台 | 配置地址、密钥、模型、默认模型；生效方式 | F17、F19、F20 | 改配置并重启实例后模型选择器随之变化 |
| 1.13 权限三档 | 权限预设表、默认档位；验证 Auto review 和 Yolo 的实际行为 | F43、D8 | 三档各跑一个写文件任务，行为与定义一致 |
| 1.14 审计 | 登录、注册、管理操作、实例事件 | F6 | 日志不含密码、密钥、对话内容 |
| 1.15 两个办公 Agent | 综合办公、公文写作，验证 preset 机制 | F21–F24（部分） | 手动指定和自然语言两种方式都产出真实 DOCX |
| 1.16 部署骨架 | compose 文件、平台镜像 | D3 | 一条命令起全套 |
| 1.17 隔离测试 | 通过接口、长连接、路径、Shell、网络访问他人数据和平台资源 | 验收 1、2 | 全部被阻止 |

**完成条件**：验收 1、2、13 的自动化测试通过；验收 3 的“不配置密钥即可完成真实工具调用”部分通过（无公网部分留到阶段 3）；验收 12 的“停止或重建后恢复”部分通过（Office 部分留到阶段 2）。

**风险与退路**：

| 风险 | 退路 |
|---|---|
| 1.0 发现目标机上沙箱无法启用 | 把默认权限档改为容器内完全权限，以容器为唯一边界；需项目方确认 |
| 1.1 找不到可靠的空闲判定 | 退为按网关侧连接和流量判定，保守设置较长的空闲时间 |
| Auto review 在开发模型上不可用 | 记录现象，Auto 档暂时等同人工批准，生产联调时用 `qwen3.6` 重测 |

**目标**：员工在知识库页面看到真实的库和文件，按 Session 选择检索范围并得到带来源的回答；DOCX、XLSX、PPTX 在线编辑保存后 Agent 读到新内容。

**必读文档**：基线 5.5、5.6；分析 2.4、3.4、3.5。

| 任务包 | 内容 | 覆盖 |
|---|---|---|
| 2.1 RAGFlow 只读代理 | 四个接口、错误码映射、无效 ID 剔除、越界校验、超时 | F26、F31、F33、F34 |
| 2.2 RAGFlow 连接后台 | 地址、密钥、连通性检测、版本显示 | F4 |
| 2.3 RAGFlow 插件：页面 | 知识库列表、展开看文件、搜索、分页、各种状态 | F27 |
| 2.4 RAGFlow 插件：选择器 | 输入区控件、Session 事件、默认全选、提交时快照 | F28–F30 |
| 2.5 RAGFlow 插件：检索工具 | 沿 `parentSession` 回溯取范围；来源展示 | F25、F32 |
| 2.6 Document Server 部署 | 镜像、JWT、字体、网络 | F41、D11 |
| 2.7 Office 接入 | 用户镜像加入两个插件和补丁；覆盖层加入 Office 配置；向 `better-sidebar` 上游提需求 | F37–F39、T6 |
| 2.8 Office 体验 | 没有 Session 时的提示；并发覆盖提示；连接数满的提示；XLSX、PPTX 验证；编辑器打开时 Agent 改文件的刷新 | F40、F42 |
| 2.9 HTML 预览验证 | 沙箱行为验证；受管配置钉死 | F36 |
| 2.10 插件目录 | 后台维护批准目录；员工页只有开关；关闭安装入口和安装工具 | F46、D9 |
| 2.11 内网联调 | 在 `192.168.2.98` 上复核三类接口和多库检索 | 验收 6–9 |

**风险与退路**：`better-sidebar` 升级后补丁失效时，构建会失败并提示；在上游支持之前停留在 0.24.1。

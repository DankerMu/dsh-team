# DSH 企业多用户办公平台：开发方案

日期：2026-10-03。本文是 `stage-change-pipeline` 的阶段输入：每个阶段给出目标、任务包、必读文档和完成条件。

- 需求依据：`docs/REQUIREMENTS_BASELINE.md`（下称“基线”，功能编号 F1–F48，决定编号 D1–D15）。
- 事实依据：`docs/DSH_Enterprise_Architecture_Analysis.md`（下称“分析”）。架构图和实测结果在那里，本文不重复。
- 验证脚本：`verify/phase0/`，一次性验证用，不是平台代码的起点。

## 1. 目标与成功标准

交付一个单机 Docker 部署的平台，满足基线全部功能需求，并通过基线第 7 节的 14 条验收。DSH 源码不改；所有定制通过平台代码、DSH 插件、受管覆盖层和镜像构建完成。

## 2. 约束与假设

| 类别 | 内容 |
|---|---|
| 约束 | DSH 源码不改（D1）；Node/TypeScript + SQLite（D2）；单机 Docker（D3）；完全离线运行 |
| 约束 | 版本钉定见基线第 4 节 |
| 假设 | 目标服务器上 bubblewrap 或 Landlock 至少一种可用。本机实测需要放宽 seccomp 和 `/proc` 屏蔽两项容器设置（分析 3.6）。阶段 1 第一个任务包验证，不成立则方案要改 |
| 假设 | `qwen3.6` 能稳定做工具调用。开发期用 `deepseek-v4.1-flash`，生产联调时重验 |
| 假设 | 内网各 RAGFlow 知识库用同一个嵌入模型。不成立则检索改为逐库请求后合并 |

## 4. 关键技术决定

阶段 0 的实测已经确定或逼出了下面这些做法。

| 编号 | 决定 | 依据 |
|---|---|---|
| T1 | 网关对上游始终使用一个固定的 authority（平台对外的 host:port），DSH 用 `--trusted-host` 放行它。不使用 `--public-url`（发行版没有） | 分析 3.2；DSH cookie 绑定请求的 Host |
| T2 | 网关读取容器 stdout 里的启动令牌，在服务端换成 DSH cookie 并保存，之后每个请求注入；浏览器只持有平台自己的登录 cookie。令牌交换用 `http.request`，不能用 `fetch` | 分析 3.2，已实测 |
| T3 | 受管覆盖层按用户生成，只读挂载，用 `--patch` 加载。内容：监听 `0.0.0.0`、模型配置、默认模型、去掉每个 preset 的联网搜索和抓取工具、Office 插件配置（含该用户容器的内部地址）、关闭 HTML 沙箱开关、权限预设。模型等部分所有用户相同，只有 Office 的内部地址按用户不同 | 分析 3.3、3.5，已实测；Office 插件的 `internalBaseUrl` 每个用户不同 |
| T4 | 容器启动命令：`dsh --profile web --patch <覆盖层> --no-open --trusted-host <authority>`；环境变量注入模型密钥和 `DSH_TELEMETRY_DISABLED` | 分析 2.3，已实测 |
| T5 | 插件和 profile 目录在镜像里预置；新用户卷首次挂载时自动带上。任务12.2另预置可写的 `storages/workspace.json`：一个 `/data/work` 工作区、空 Session 索引，仅填充空状态卷，不迁移或覆盖已有工作区、Session 和文件。镜像升级时老用户卷的 profile 目录由平台在启动前同步；该同步不含 storages | 分析 3.6；profile 首次填充已实测，同步逻辑待做；任务12.2由真实网关/浏览器 Docker 回归验证 |
| T6 | `better-sidebar` 0.24.1 的补丁由用户镜像的构建步骤维护，版本不符时构建失败。同时向上游提需求 | 分析 3.5，已实测 |
| T7 | 每个容器 `--hostname` 取用户 ID 派生的唯一值 | 分析 3.5 |
| T8 | 容器安全设置：自定义 seccomp 配置放行用户命名空间相关调用，并解除 `/proc` 屏蔽。本机验证用的是整体关闭 seccomp，正式配置在目标机收敛 | 分析 3.6 |
| T9 | 网络：每个用户容器一个独立网络，网关和 Document Server 接入各网络。具体做法在阶段 1 验证 | 基线 F11 |
| T10 | RAGFlow 知识库选择存为 Session 事件（标记为可忽略），提交任务时快照；检索工具沿 Session 的 `parentSession` 回溯到根 Session 取选择 | 分析 3.4；`parentSession` 字段已实测，插件代码待写 |
| T11 | 插件前端与后端通信用插件自己注册的普通 HTTP 路由，不用 DSH 的类型化远程调用生成器 | 分析 2.3 |
| T12 | 平台不实现模型代理；不为每个用户申请独立密钥 | 基线 D7 |

阶段1按需启动的运行边界：索引容器精确404与账号/实例快照核验通过后，原编排器立即通知进程生命周期服务该旧身份已缺失；镜像解析失败不得让旧运行行继续转发。应用关闭与主进程信号先关闭启动和网关连接准入，再等待实际编排工作/队列完成，最后关闭SQLite。后台开发停止保留捕获的PID直到真实优雅退出；并发启动/停止明确拒绝，不把旧监听器健康当成新进程就绪。共享Engine的e2e隔离仍由[#176](https://github.com/DankerMu/dsh-team/issues/176)单独跟进，不宣称已有独占保障；watcher问题#174不在本次范围。

阶段1网关活动记录：`app.getUserActivity(userId)` 返回当前进程的 `{ liveCount, lastActivityAt }`，复用已认证响应/升级连接的登记和释放；HTTP响应结束后保留的keep-alive socket不计数，连接存活无需流量心跳。仅既有 `instances.last_activity_at` 持久化，时间为epoch毫秒；写入沿原编排器每用户FIFO排队，合并最新观察，每用户成功写入至少间隔60秒，缺失行不创建、既有较新时间不回退。失败以固定安全日志报告，留待正常周期处理，不阻断转发或引入重试循环。退出先停止定时器并关闭准入/传输/监听器，在 `onClose` 结清到期活动及生命周期队列后关闭SQLite；不足一分钟的尾部观察不突破限频或延迟退出。

阶段1空闲回收：应用每60秒触发一次不重叠检查，读取当次 `settings.idleMinutes`。仅实际 DSH 的完整、匹配 `session/list` 回应能判定任务空闲；运行中、超时、鉴权失败、畸形或不完整回应都会清空连续空闲区间。第一次明确空闲才开始计时，不以历史活动时间推断任务早已完成。到期停止沿原每用户FIFO，再核验实例身份、连接/活动、显式启动及最新配置；仅已准入的停止暂时阻止该身份继续转发。停止原因为 `idle`，保留状态卷和工作卷；退出取消探测并等待已准入停止结清，不增加持久状态或第二队列。可控时钟真实Docker四场景与独立source/dist运行验证覆盖阈值、已打开连接、同实例真实Agent任务以及30→5分钟即时生效。

阶段1回收后恢复（任务12.5）：同一有效平台会话请求首页得到等待页重定向，GET不隐式启动；调用既有启动接口后，新物理容器使用原两个卷。真实Docker验收保留同一Session ID、完整用户/助手历史（包括运行上下文事件）及含中文、NUL和非UTF-8字节的工作文件；不重新登录、不重建Session、不在重启夹具中回填用户数据。Docker挂载元数据按目标路径比对，数组顺序不是持久性合同。独立source/dist真实运行验证同cookie等待/启动/HTML及文件恢复；真实对话历史另由永久Docker场景证明。仅保证已完成对话和文件保留，不承诺被中断任务继续；等待页界面仍由第13组交付。

阶段1不可用状态与重试（任务12.6）：模型未配置返回 `unconfigured`，容量满返回 `full`，不分配用户资源或驱逐运行中实例；真实就绪失败保留已停止的出错容器、清除DSH cookie并保留脱敏日志。仅显式重试且配置/容量准入成功后，原每用户FIFO通过既有精确归属停止路径退役旧error身份（reason=`error`），核验账号及完整终态快照，再重新生成受管配置并启动新容器；不删除两卷。状态、身份、账号、取消或退役/审计失败不得继续创建。启动身份检查集中于 `start-identity.ts`，凭据、就绪、对账和停止复用同一实现。真实公开API及独立source/dist Docker烟测均覆盖保留error容器→同会话重试→真实DSH；外部删除running容器且降低上限的另一路状态分类问题仍由[#177](https://github.com/DankerMu/dsh-team/issues/177)处理。

阶段1前端包与浏览器验证（任务13.1–13.2）：`platform/web` 使用React18/Vite构建到 `platform/web/dist`，仅声明 `/_platform/login` 和 `/_platform/assets/*`；不存在的平台/API路径保持404，不用SPA回退吞掉接口错误。静态文件经显式dotfile拒绝、realpath根边界和普通文件检查后由标准插件流式提供，支持HEAD/MIME/范围请求；源码与构建后的平台共用相同目录定位。生产入口缺少或无法读取构建时在监听前失败；`buildApp` 的离线注册不依赖产物。`pnpm build`、开发及集成/UI命令建立产物，后台开发仅在持有启动锁且确认无既有实例后构建，避免重复启动清空运行中的资源。

`pnpm test:ui:install` 显式安装固定Playwright Chromium；`pnpm test:ui` 在独占端口、独立SQLite及真实平台路由上加载编译后的React表单，截图保存在 `reports/platform-ui/`，要求零控制台/页面错误且无站外请求。CI的UI job纳入必需汇总门禁；撤销UI延期项，并以拒绝canary证明新TSX配对/类型/覆盖率与浏览器模块边界门禁生效。此切片的表单凭据控件禁用、不提交、不序列化密码；实际登录由13.3交付，等待/后台页面不在本项。浏览器安装仅为验证依赖，不进入离线生产运行时。

浏览器死代码门禁另有独立拒绝canary：经真实Vite入口导入一个不消费其导出的模块，要求Knip明确报告该导出；隔离烟测确认屏蔽整个浏览器工作区会导致漏报，从而被该canary识别。后台死代码拒绝用例不能替代浏览器工作区的证明。

# Compose deployment

The delivered `deploy/compose.yml` and how `pnpm test:deploy` verifies it.

Moved verbatim from the root `AGENTS.md`; normative behaviour lives in the OpenSpec specs (`openspec/specs/`, `openspec/changes/`). Keep this file current in the same change as the code it describes.

## Compose deployment verification

`deploy/compose.yml` consumes the separately built `dsh-team-platform:local` and configured user image. It retains image uid1000, fixes the platform container name to `dsh-team-platform` and upstream mode to `network`, and publishes only the platform port. From the repository root use `docker compose --project-directory . --env-file .env -f deploy/compose.yml up -d`; interpolation and the explicit container environment mapping use the same root configuration copy.

The same command starts the bundled Document Server: `onlyoffice/documentserver:9.4.0` with the literal container name `dsh-team-documentserver`, JWT enabled, `ALLOW_PRIVATE_IP_ADDRESS=true`, no published host port, and the operator font directory `assets/fonts/` at the repository root bound read-only (without host-path creation) to `/usr/share/fonts/truetype/custom`. `.env` must set a nonempty random `DOCUMENT_SERVER_JWT_SECRET`: Compose passes that one value to both the Document Server (`JWT_SECRET`) and the platform, and an unset or empty value fails interpolation before any container is created. The platform also receives the literal `DOCUMENT_SERVER_CONTAINER_NAME=dsh-team-documentserver`; the platform reads both at startup (both absent: the bundled Document Server is unconfigured and Office unavailable; one absent, either empty, or an invalid container name: startup fails before listening, naming the variable without echoing values), and instance attachment belongs to 16.3.

Require Docker Compose 2.33.1 or newer and a Docker Engine supporting endpoint gateway priority (verified on Engine29.1.3). The primary Compose network has `gw_priority: 1`; dynamically attached employee networks retain priority0. Without this, attaching an employee network can change the platform's default gateway and drop an in-flight public request even while a new health connection succeeds. Do not replace gateway priority with connection-order `priority`, request retries or host networking.

For that copy, set `PLATFORM_HOST=0.0.0.0`, the actual public origin, and absolute data/managed-config directories pre-created writable by uid1000. Their bind source and destination are identical, with automatic host-path creation disabled. Set `DEPLOY_DOCKER_GID` to the actual socket's numeric group (`stat -c %g /var/run/docker.sock` for the default socket). Do not run the platform as root, alter socket permissions, or hardcode a verification host's group. Compose deliberately fixes transport/name; host-only `published-loopback` configuration is not used for this deployment.

Optional subnet, cookie-security and log-level defaults apply only when absent; explicit empty values reach the existing validators and fail naming the input. Compose must not silently replace invalid blanks with defaults.

Create the administrator with `docker compose --project-directory . --env-file .env -f deploy/compose.yml exec platform node platform/dist/cli.js admin create <email>` from a real terminal. Do not add `-T` or pass passwords as arguments/environment; the CLI already receives the deployed configuration inside its container.

`pnpm test:deploy` runs the deployment files (`deployment.docker.test.ts`, then `deployment-document-server.docker.test.ts`) directly in the existing serial Docker project on trusted giap-vps, without provisioning a browser or calling a model. It requires Linux amd64, non-root uid1000 and util-linux `flock`; the kernel lock spans admission through cleanup. A pre-existing fixed platform or Document Server container is refused without adoption/removal. Test overrides supply only captured image/owned resource identities, never a substitute platform or administrator database seed. The one permitted substitute is the Document Server stand-in: the giap-vps disk cannot hold the real image, so `test:deploy` runs `documentserver` from the invocation's captured platform image with an idle entrypoint and an owned empty font directory; the real image runs only in the local `pnpm test:stack` lane. The fixture injects a fresh per-invocation non-secret JWT that stays in the 0600 env file and container environments; assertions compare only booleans and SHA-256 digests. A separate case writes the configuration with that key unset and with it empty, and requires `compose up` to fail naming the variable before any owned container or network exists. Register stable Compose/employee resources before creation and use canonical ownership-checked cleanup; production composition helpers retain their existing exact-invocation cleanup. Unknown discoveries never become deletion authority.

All deployment entrypoints share the host-wide `/tmp/dsh-team-deployment.lock`, independent of an invocation's private `TMPDIR`. The lock is held through canonical cleanup and is never unlinked to release or take it over. On Linux `flock --nonblock` holds it; on macOS (the local `pnpm test:stack` lane only) `/usr/bin/python3` holds the same file with `fcntl.flock` exclusive non-blocking, with the same `locked` handshake, stdin-EOF release and release on holder death. Real Linux contention coverage holds the actual deployment lifecycle while a distinct-TMPDIR subprocess attempts admission, requires exclusion before Docker work, then proves admission after release.

Before destructive fixture cleanup, signal only the invocation-verified platform ID with SIGTERM and wait for graceful exit while the lock remains held. A forced stop is not proof of owner drainage; retain the scenario error and append drain/cleanup failures. The failure-path regression blocks the real composition helper on an owned FIFO, subscribes independently to exact owner/helper Docker events before aborting the caller, and requires helper destruction before graceful owner exit. Emergency cleanup uses only captured, ownership-verified identities after recording any regression failure. The custody owner's post-cancellation retirement shares this one drain and the same non-blocking lock holder (stdin-EOF release, never unlinked): a run that registered its own fixed platform is drained only under that lock, and an unavailable lock or unconfirmed drain removes nothing of the run.

Deployment privacy/audit verification emits one bounded `deploymentSetup` JSON report after the existing lifecycle settles. Closed-set entered/completed/failed phases distinguish the unfinished parent from its completed child; the first failure remains latched with `cause: unknown`. Platform drainage, resource cleanup and observation retirement report their own actual outcomes independently of the primary failure. Sanitized rejection carries the same safe `setup` facts; unavailable output is marked `setup-evidence-unavailable`, without retrying or exposing source/sink messages, nested causes, arguments, credentials or conversation content. `pnpm test:integration` qualifies these failure-composition and secrecy boundaries without Docker; original full Docker and standalone deployment acceptance remain required. A later successful run does not explain historical setup failures lacking retained causal evidence.

Platform persistence acceptance recreates only the drained, exact-owned platform container through the same Compose recipe while two employee containers remain running. Require a different platform ID, unchanged employee IDs/StartedAt/restart counts/mounts/network identities, fresh login for all existing accounts and distinct native Session readback. Compare model projection plus a nonsecret settings digest and exact audit rows before new logins legitimately append events; never seed the database or reconnect employee networks manually.

With two ready native instances, exposure acceptance inventories the union of invocation, Compose-project and exact employee labels, including additional deployment containers. Check configured and effective host bindings: only the platform's configured TCP port is published (IPv4/IPv6 bindings of that port count once; null image EXPOSE entries do not count). Other deployment containers have no publication, host/shared-container network bypass or Docker socket bind, including alternate socket targets and resolved ancestor bind sources. Discovery is read-only and never expands cleanup authority; this is not a claim about every possible Docker-access mechanism.

HTTPS acceptance requires host `openssl` for ephemeral SAN certificates and adds only an owned test Compose proxy. The platform remains HTTP behind it, with HTTPS public authority, Secure session cookies and the inspected proxy's exact trusted IP. Clients trust only that invocation's certificate; no global TLS disablement. Require authenticated native HTML, same-carrier WSS Ping/Pong and a specific login audit matching independently captured proxy socket-peer telemetry despite forged incoming forwarding headers. Certificate/private-key contents and cookie tokens never enter diagnostics. This checks server cookie attributes and transport, not browser enforcement or rendering.

Required evidence is actual health200, real TTY administrator creation without input leakage, authenticated model configuration and fresh employee startup, native DSH HTTP200/WebSocket101, same-path mounts and unpublished instance ports. Native entry also covers transfer through the gateway over `node:http`: the combined plugin script is gzip-encoded only when requested (decoded bytes equal the identity body), `/plugins/events` stays an uncompressed event stream, and the HTML-named hashed `/assets/` entry script gains the gateway's `private, max-age=31536000, immutable` while the HTML, the event stream and the combined plugin script (DSH's own `public` immutable header) do not; the gateway applies that header to every Vite-hashed DSH `/assets/` js/css/font file (GET/HEAD 200, no query, no upstream `Cache-Control`). This is transport/entry evidence, not browser rendering or provider inference. Both standalone `pnpm test:deploy` and the original full `pnpm test:docker` must run on the frozen head; full discovery includes `deployment.docker.test.ts`, so the existing owner `dsh-team/docker` CI attestation covers the deployed surface rather than substituting a historical Docker pass. Final inventories include the fixed platform name, `dsh-team-documentserver` and `dsh-team-compose-*` helpers as well as existing owned prefixes.
